## 1. Executive Technical Summary

### 1.1 What AquaRizz is

AquaRizz is an AI-assisted decision-support system for urban flooding in Chennai. It ingests rainfall observations, rainfall forecasts and drain water-level readings; forecasts drain levels 15 to 120 minutes ahead; estimates a calibrated flood-hazard index per ward; combines it with exposure and vulnerability into a risk level; explains the result with evidence; drafts recommendations, candidate evacuation routes and an alert; and then stops. A human reviewer approves, modifies or rejects. Only an approved alert can be dispatched, and the database itself enforces that rule. Outcomes are recorded and fed to a controlled offline learning loop.

AquaRizz is decision support, not an autonomous system. No language model produces any flood number. No alert leaves the system without a recorded human approval.

### 1.6 Definition of demo-complete

The prototype is demo-complete when one command starts the stack and the scripted scenario (§43) runs end to end with: simulated sensors posting through the production HTTP contract; hazard and risk rising on the map; an explanation with evidence links; a pending alert draft; a refused approval by an unauthorised role; an approved alert dispatched to a sandbox inbox and a mocked phone; three candidate routes that avoid a flooded underpass; a recorded outcome; and a learning evaluation with before/after metrics, every one labelled as in §1.4 and §47.

### 1.7 What AquaRizz is not

It is not an official warning system, a validated inundation model, a replacement for IMD or GCC procedures, or an autonomous responder. Its thresholds are PROTOTYPE values. Its sensor data and model skill are synthetic until real telemetry and labelled events are integrated.

## 3. Design Principles and Non-Negotiable Constraints

### 3.1 Principles

| ID | Principle | Consequence |
| --- | --- | --- |
| P1 | Decision support, not decision making | Every action that reaches the public needs a recorded human approval |
| P2 | Numbers come from models, never from a language model | The LLM receives structured facts and may only phrase them; output is validated |
| P3 | Evidence or silence | Every claim in an explanation cites an evidence id that resolves to a stored value |
| P4 | Abstain rather than guess | Missing or stale inputs produce INSUFFICIENT\_EVIDENCE with the reason, never a silent default |
| P5 | Simulated is never shown as real | Labels in the data, API and UI; badge on every simulated value |
| P6 | Deterministic core, optional intelligence | Risk, policy and attribution are pure functions; the LLM is optional |
| P7 | One path for real and simulated inputs | The simulator posts to the same HTTP endpoints as real devices would |
| P8 | Space and time are explicit | Typed geometry with SRID 32644 enforced by CHECK; timestamptz in UTC |
| P9 | Prototype is not official | Policy files carry official: false until an authority supplies thresholds |
| P10 | Reproducible | Seeds, config hash, data manifest and model hash stored with every run |
| P11 | Fail visibly and safely | Degraded modes lower confidence and say so; data loss never causes a silent downgrade |
| P12 | Hazard gates risk | Exposure and vulnerability can raise severity only inside the band that hazard permits |
| P13 | Boring technology | One database, one language for the backend, one deployment unit |
| P14 | Honest evaluation | Baselines in every table; no claim without a run id |

### 4.2 Runtime topology

```
[browser: control room, citizen map] --HTTPS--> [web (nginx, static)] --> [api (FastAPI)] --SQL--> [db (PostGIS)]
[simulator process] --HTTP (same contract as devices)--> [api] ;  [worker (APScheduler)] --SQL--> [db]
[worker] runs: connectors, analysis graph (LangGraph), dispatch graph, learning jobs
[dispatcher service] --SMTP--> [mailpit sandbox inbox] ; SMS, IVRS, push --> simulated gateway rows
[optional] ollama (local LLM) · prometheus + grafana
```

The api and worker share one Python package and one image. The worker is the only place where the analysis graph runs automatically; the api can also start a run on demand.

### 4.5 Time and clocks

All stored timestamps are timestamptz in UTC; the UI shows Asia/Kolkata. Rainfall rows carry period\_start and period\_end. Every component that needs 'now' calls a clock service that returns real time normally and the simulated clock during a scenario run; freshness and lateness checks use that clock, otherwise every replayed reading would be flagged late. The analysis cadence is every 10 minutes of clock time, and every 5 minutes while any ward is MEDIUM or above or an ingest trigger condition holds (§23.3).

## 5. Architecture Decision Records (ADR-001 to ADR-013)

Each record states the decision, the alternatives rejected and the consequences. The last line of each record is the only place in this guidebook where the two earlier source guides are compared (Guide 1 = the guide that used the ews package name and a deterministic ramp-based hazard; Guide 2 = the guide that used a logistic hazard and dual geometry columns).

### ADR-001 — Modular monolith with LangGraph orchestration

**Decision.** One Python package, one container image (api and worker), enforced package boundaries (§4.3). LangGraph runs two graphs, an analysis graph and a dispatch graph (§23). Agents are typed classes; routing between nodes is decided by code, never by a language model. **Rejected.** Microservice per agent (operational cost with no benefit at this scale); free-form multi-agent conversation frameworks (non-deterministic control flow, weak audit); plain scripts (no explicit state, poor traceability). **Consequences.** One deployment unit; boundaries are checked by import-linter in CI; typed contracts make later extraction possible. **Reconciliation.** Both guides chose a monolith with LangGraph. Guide 1 used two graphs; Guide 2 used one graph plus a dispatcher. Two graphs are adopted. Package name is `aquarizz`.

### ADR-002 — PostgreSQL 16 + PostGIS 3.4 as the only datastore

**Decision.** Everything is stored in one PostgreSQL 16 database with PostGIS 3.4: static layers, observations, forecasts, assessments, reviews, audit. Time series are ordinary tables indexed on (sensor\_id, observed\_at). Work queues use advisory locks and SELECT ... FOR UPDATE SKIP LOCKED. Model artifacts live on a mounted volume with a SHA-256 stored in model\_versions. Similar-event retrieval is a standardised Euclidean distance over five features, not a vector search. **Rejected.** Redis (no caching need), Kafka or MQTT (about 69 thousand sensor rows per simulated day), TimescaleDB (extension cost for no gain), MinIO (artifacts fit on a volume), a vector database (no embeddings), Kubernetes. **Consequences.** One backup target; transactional integrity between reviews and alerts; monthly partitioning is the first scale step (§40). **Reconciliation.** The guides agreed. Neither adds a second datastore.

### ADR-003 — Spatial units and coordinate system

**Decision.** The GCC ward (about 200) is the operational unit for assessment, alert and approval. The 250 m cell is the modelling and footprint unit. The 15 GCC zones group wards and place background sensors only. Every stored geometry is typed with SRID 32644 (WGS 84 / UTM zone 44N). Boundaries convert to EPSG:4326 only at the API edge (GeoJSON, RFC 7946); MapLibre handles its own display projection. **Rejected.** Dual geometry columns for 4326 and 32644 (duplicate state that can disagree); zones as the operational unit (too coarse for alert targeting and routing); 100 m cells (the 30 m surface model has vertical error comparable to Chennai's relief); H3 hexagons (no benefit over a plain grid joined to wards). **Consequences.** All distances are metres; no geography casts in spatial queries; every API output passes through one transform helper. **Reconciliation.** Guide 2 stored both CRSs through a trigger; Guide 1 stored 32644 only, which is also the native CRS of the GCC service. 32644 only is adopted.

### ADR-004 — M1 flood susceptibility: LightGBM with spatial validation

**Decision.** M1 is a LightGBM binary classifier at 250 m cell level using terrain, drainage and land-cover features. Historical flood frequency is excluded from M1 inputs because the labels are derived from the same events. Labels are presence points and polygons with pseudo-absences at least 750 m from any positive and outside the GCC high-hazard zones. Validation is buffered spatial block cross-validation (5 km blocks, 500 m buffer, 5 folds) plus leave-one-event-out when at least two independent events exist. The output is the percentile rank of the model score across the study area, so S is a relative susceptibility index in \[0, 1\], not a probability. Below 150 positive cells the system falls back to a fixed-weight index. **Rejected.** Random k-fold (spatial leakage inflates AUC); a CNN on the surface model (too few labels); reporting probabilities from pseudo-absence training (prevalence is arbitrary). **Consequences.** S is stable under changes of the pseudo-absence ratio; reported AUC is a relative-ranking metric, so the Continuous Boyce Index and an independent overlap check against GCC hazard zones are also reported. **Reconciliation.** Both guides used LightGBM. Guide 2 fed historical frequency into M1, which leaks labels; it is removed. Rank scaling and the 150-cell gate come from Guide 1.

### ADR-005 — M2 water-level forecast: LightGBM quantile regression

**Decision.** M2 predicts the change in drain water level, delta h = level(t + tau) - level(t), for tau = 15, 30, 60 and 120 minutes at quantiles 0.1, 0.5 and 0.9, one LightGBM model per (horizon, quantile), 12 boosters in total. Quantile crossings are repaired by sorting. A horizon is enabled in production only if it beats persistence and linear extrapolation on the domain-shift test set and its P10 to P90 coverage lies between 0.70 and 0.90; otherwise that horizon returns null with a reason. All results are SYNTHETIC-VALIDATION. A linear-extrapolation fallback runs whenever a model file is missing or its hash fails. **Rejected.** GRU or LSTM (no real telemetry to justify them; kept as a notebook experiment with a stated gate, §15.7); predicting absolute level (hides skill behind persistence); one multi-output network (opaque, no per-horizon gating). **Consequences.** The +120 minute horizon is an outlook that shapes a watch flag, not the headline level (§18). **Reconciliation.** Guide 1 forecast 15, 30 and 60 minutes and used rainfall-based drain stress beyond that; Guide 2 listed four horizons. Four horizons with skill gating are adopted.

### ADR-006 — M3 hazard: calibrated logistic function

**Decision.** Hazard is H = sigmoid((z - b) / T) with z = b0 + sum of w\_k f\_k over seven ramp-normalised features (§16). Weights are ASSUMED engineering priors labelled PROTOTYPE. The calibration status ladder is UNCALIBRATED, SYNTHETIC\_CALIBRATED, HINDCAST\_CALIBRATED, OUTCOME\_CALIBRATED. The default calibration method is a two-parameter logit recalibration (intercept shift b and temperature T) because it is monotone and stable with few labels; isotonic regression is allowed only after 500 outcome-paired ward-horizons including 50 positives. **Rejected.** A black-box classifier (no labelled ward-level hazard data); the probabilistic-OR of ramp functions (not statistically estimable, cannot be calibrated); a weighted sum of hazard, exposure and vulnerability as the hazard itself (compensatory). **Consequences.** H is displayed as a likelihood index until calibration status leaves UNCALIBRATED. The physically motivated drain stress from SCS-CN and Manning enters as a feature used only when sensors are unavailable. **Reconciliation.** Guide 1 composed ramps by probabilistic OR; Guide 2 used a logistic with eleven features. A logistic with seven features is adopted and Guide 1's drain-stress physics is kept as the sensor-substitution feature.

### ADR-007 — Hazard-gated risk classification

**Decision.** Hazard band decides which risk levels are permissible. Impact (from exposure and vulnerability) selects within the permitted pair of levels. Deterministic safety floors, driven only by hazard evidence, may raise the level above the band. Confidence never changes the level; it governs review rules and which actions may be drafted. Data loss never lowers a level by itself, and de-escalation needs hysteresis (§18). **Rejected.** A compensatory weighted sum of H, E and V (a dry day over a dense vulnerable ward could trigger an alert); a multiplicative gate on a weighted sum (still compensatory, with arbitrary cut-offs); capping the level when confidence is low (turns uncertainty into false reassurance). **Consequences.** Exposure cannot create an alert on its own; a low-confidence VERY\_HIGH remains visible and is routed to a human with a LOW-CONFIDENCE tag. **Reconciliation.** Guide 1 used R = G(H) x (0.4H + 0.3E + 0.3V) with a confidence cap; Guide 2 used a hazard-by-impact matrix. The matrix is adopted with Guide 1's band cut-points (0.10, 0.40, 0.70), and the confidence cap is replaced by the governance gate.

### ADR-008 — Six agents and two graphs

**Decision.** Six agents (Orchestrator, Data & Retrieval, Forecasting, Flood Risk Analysis, RCA & Explanation, Decision & Recommendation) and three services that are not agents (human oversight, dispatcher, learning). Agents exchange typed contracts and call only typed tool wrappers. **Rejected.** Language-model-planned routing; agents with direct SQL; one agent per model. **Reconciliation.** Both guides defined the same six agents; contracts are merged.

### ADR-009 — LLM modes

**Decision.** LLM\_MODE is off, template or llm. Template is the default; llm lets a local model paraphrase already-computed facts, and the output is validated and discarded on any failure. Tests and demos run with the LLM off. **Rejected.** Free-form generated explanations; any use of an LLM for numbers, routing or approval; a hard dependency on a cloud model.

### ADR-010 — Database-enforced human approval

**Decision.** Alert status is one of ten values: DRAFT, PENDING\_REVIEW, APPROVED, DISPATCHED, OUTCOME\_CAPTURED, REJECTED, EXPIRED, ABSTAINED, INSUFFICIENT\_EVIDENCE, FAILED. A trigger refuses DISPATCHED unless an APPROVE review exists for the same alert and the same version. Reviews and audit rows are append-only; the audit log is hash-chained. Superseded and cancelled alerts become EXPIRED with a reason code. **Rejected.** Application-level checks only; timeout-as-consent; a boolean approved flag. **Reconciliation.** Guide 1's database guard and version binding are adopted. Guide 2's extra states (SUPERSEDED, CANCELLED, ACTIVE, RESOLVED) are mapped to reason codes so the canonical list stays at ten.

### ADR-011 — Routing with OSMnx and NetworkX

**Decision.** A drive graph from OpenStreetMap, built once per month, with Dijkstra search over a cost of travel time multiplied by (1 + 4 x edge risk); edges at risk 0.9 or above are removed. Three candidate routes per origin are produced and ranked by a safe-route score. **Rejected.** Commercial routing APIs (cost, terms, no risk penalty); pgRouting (an extra extension with no benefit at this graph size).

### ADR-012 — Docker Compose on one machine

**Decision.** Compose profiles for the core stack, demo, optional LLM and observability. A laptop with 16 GB RAM (8 GB with the LLM off) runs everything. **Rejected.** Kubernetes, serverless functions.

### ADR-013 — Controlled offline learning only

**Decision.** Learning is an offline job that pairs predictions with outcomes, computes metrics, proposes a calibration or retraining candidate and stops. Promotion to ACTIVE needs shadow evaluation, passing tests and a recorded human approval. **Rejected.** Online learning; automatic promotion; reinforcement learning.

### 7.2 Source decisions taken

| Question | Decision |
| --- | --- |
| Which DEM | GLO-30 from the AWS bucket; probe on first run; fall back to SRTM 30 m then GLO-90; always recorded in the manifest |
| Are drain attributes usable | Treated as present but sparse; completeness is measured per ward and the drain capacity index is computed only from complete edges |
| Shelter data | Digitise D13; capacity stays null; never imputed (R11) |
| Flood labels | D12 points and polygons; D14 optional; no labels for 2023 unless D15 is processed |
| Forecast horizon | 15 to 120 minutes comes from sensor dynamics plus hourly NWP; no 15-minute rainfall nowcast skill is claimed |
| Tide | Simulated only |
| Demo ward | Chosen by rule (§43.2), not by name |

### 7.3 Probe script

`scripts/probe_sources.py` runs in Phase 2 and before every demo. It requests layer metadata and returnCountOnly from the GCC service on both host names, checks the layer count (expected nine) and field names, makes one Open-Meteo forecast and one archive request, sends a HEAD request for a DEM tile, and writes SHA-256 hashes, row counts, retrieval time and a status (VERIFIED, FAILED\_PROBE, UNVERIFIED) per source into data/MANIFEST.yaml and the data\_sources table. A required source that fails without a configured fallback stops the build.

### 7.4 Training and validation separation

| Rule | Reason |
| --- | --- |
| Forecasts are joined to observations only where issued\_at is not later than the analysis time | Prevents using the future |
| Post-event flood polygons are never visible before the event end | Label leakage |
| One event is never in both training and test | Event-level independence |
| For M1, cells within 500 m of a test block are removed from training | Spatial leakage |
| Historical flood frequency is not an M1 input | It is derived from the labels |
| M2 is split by storm, not by row | Rows within a storm are strongly dependent |

## 8. Data Architecture, Provenance and Labelling

### 8.1 Data zones

```
 raw (immutable files + manifest)  ->  staging (parsed, typed)  ->  curated (PostGIS tables)  ->  features (as-of, versioned)
   data/raw/<source>/<date>/           data/staging/                   45 tables (§9)                runs/<run_id>/features.parquet
                                                                                                    |
   models (registry + artifacts) <- training sets (manifest hash) <------------------------------------+
   assessments, evidence, explanations, alerts, audit  (written only by the analysis and oversight code paths)
```

### 8.2 Provenance rules

| Rule | Mechanism |
| --- | --- |
| Every curated row names its source | source\_id foreign key to data\_sources |
| Every simulated row is marked | is\_simulated = true and scenario\_run\_id set; simulated rows are deleted by scenario\_run\_id |
| Every analysis run is reproducible | agent\_runs stores config\_hash, data manifest hash, model ids and the clock time |
| Every explanation cites stored values | evidence\_items rows with content\_hash |
| Every model is traceable | model\_versions stores git sha, dataset manifest hash, parameters, metrics and artifact SHA-256 |

### 8.3 Label propagation

Labels travel with the data. Database rows carry is\_simulated and, for model outputs, calibration\_status and trained\_on\_simulated. Every API response includes a labels array (for example SIMULATED, PROTOTYPE, SYNTHETIC-VALIDATION, UNCALIBRATED). The UI renders one badge per label and refuses to hide them. An alert or message that was built from any simulated input carries uses\_simulated\_inputs = true and says so in its text.

### 8.4 Retention

Observations are kept 90 days in the MVP; run traces 30 days; simulated rows until their scenario run is deleted; audit logs and human reviews are never deleted. Retention is configuration, and a purge job logs what it removed.

### 8.5 Data volumes

48 sensors at one reading per minute give about 69 thousand rows per simulated day. At a 10-minute cadence, 200 wards and 5 horizons give about 144 thousand assessment-horizon rows per day. These volumes fit a single PostgreSQL instance with ordinary indexes.

```sql
-- legal status transitions and the dispatch guard
CREATE FUNCTION alerts_guard() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF NEW.status = OLD.status THEN RETURN NEW; END IF;
  IF NOT ((OLD.status, NEW.status) IN (
      ('DRAFT','PENDING_REVIEW'),('DRAFT','ABSTAINED'),('DRAFT','FAILED'),('DRAFT','EXPIRED'),
      ('PENDING_REVIEW','APPROVED'),('PENDING_REVIEW','REJECTED'),('PENDING_REVIEW','EXPIRED'),('PENDING_REVIEW','FAILED'),
      ('APPROVED','DISPATCHED'),('APPROVED','EXPIRED'),('APPROVED','FAILED'),
      ('DISPATCHED','OUTCOME_CAPTURED'),('DISPATCHED','EXPIRED'))) THEN
    RAISE EXCEPTION 'illegal alert transition % -> %', OLD.status, NEW.status;
  END IF;
  IF NEW.status = 'APPROVED' AND NOT EXISTS (SELECT 1 FROM human_reviews r WHERE r.alert_id = NEW.alert_id
      AND r.alert_version = NEW.current_version AND r.decision IN ('APPROVE','APPROVE_WITH_MODIFICATIONS')) THEN
    RAISE EXCEPTION 'no approving review for alert % version %', NEW.alert_id, NEW.current_version;
  END IF;
  IF NEW.status = 'DISPATCHED' AND NOT EXISTS (SELECT 1 FROM human_reviews r WHERE r.alert_id = NEW.alert_id
      AND r.alert_version = NEW.current_version AND r.decision IN ('APPROVE','APPROVE_WITH_MODIFICATIONS')) THEN
    RAISE EXCEPTION 'dispatch refused: alert % version % has no approving review', NEW.alert_id, NEW.current_version;
  END IF;
  NEW.updated_at := now();
  RETURN NEW;
END $$;
CREATE TRIGGER alerts_guard_t BEFORE UPDATE OF status ON alerts FOR EACH ROW EXECUTE FUNCTION alerts_guard();

-- a new version may only be added while the alert is still being drafted or reviewed
CREATE FUNCTION version_guard() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  IF (SELECT status FROM alerts WHERE alert_id = NEW.alert_id) NOT IN ('DRAFT','PENDING_REVIEW') THEN
    RAISE EXCEPTION 'alert % is not editable', NEW.alert_id;
  END IF;
  RETURN NEW;
END $$;
CREATE TRIGGER version_guard_t BEFORE INSERT ON alert_versions FOR EACH ROW EXECUTE FUNCTION version_guard();

-- hash-chained audit append (pure SQL; no extension needed)
CREATE FUNCTION audit_append(p_actor uuid, p_role text, p_action text, p_etype text, p_eid text, p_detail jsonb)
RETURNS bigint LANGUAGE plpgsql AS $$
DECLARE prev text; ts timestamptz := clock_timestamp(); h text; rid bigint;
BEGIN
  PERFORM pg_advisory_xact_lock(7001);
  SELECT row_hash INTO prev FROM audit_logs ORDER BY audit_id DESC LIMIT 1;
  prev := coalesce(prev, '');
  h := encode(sha256(convert_to(prev || '|' || to_char(ts AT TIME ZONE 'UTC', 'YYYY-MM-DD HH24:MI:SS.US') || '|' || coalesce(p_actor::text, '') || '|' ||
        coalesce(p_role, '') || '|' || p_action || '|' || p_etype || '|' || p_eid || '|' || p_detail::text, 'UTF8')), 'hex');
  INSERT INTO audit_logs (occurred_at, actor_id, actor_role, action, entity_type, entity_id, detail, prev_hash, row_hash)
  VALUES (ts, p_actor, p_role, p_action, p_etype, p_eid, p_detail, prev, h) RETURNING audit_id INTO rid;
  RETURN rid;
END $$;
```

## 10. Geospatial Architecture and CRS Rules

### 10.1 Coordinate systems

| CRS | Use | Never use for |
| --- | --- | --- |
| EPSG:32644 (WGS 84 / UTM zone 44N; Chennai is near 80.2 degrees east, inside the zone's 78 to 84 degree band) | All stored geometry, all distances and areas, the 250 m grid, all raster alignment | Nothing; it is the working CRS |
| EPSG:4326 | API input and output (GeoJSON, RFC 7946), sensor latitude and longitude, Open-Meteo requests | Distances, areas, spatial joins |
| EPSG:3857 | Map rendering inside MapLibre only | Anything stored or computed |

Rules: (1) every inbound coordinate is transformed once at the boundary with ST\_Transform(ST\_SetSRID(ST\_MakePoint(lon, lat), 4326), 32644); (2) every outbound geometry is ST\_AsGeoJSON(ST\_Transform(geom, 4326), 6); (3) raster transforms are multiples of 25 m so that 10 by 10 blocks fit a cell exactly; (4) a CHECK or typed column enforces SRID 32644 on every geometry; (5) the GCC service is requested as GeoJSON in EPSG:4326 and reprojected locally, because GeoJSON coordinates in a projected CRS are easy to misread downstream.

### 10.2 Spatial hierarchy

GCC zone (15) contains wards (about 200); a ward contains 250 m cells (about 6,800 in total). Cells are aligned to multiples of 250 m in EPSG:32644: ix = floor(x / 250), iy = floor(y / 250). A cell belongs to the ward that contains its centroid; this keeps every cell in exactly one ward and every aggregate additive.

### 10.3 Static build pipeline

`scripts/build_static.py` runs the following steps in order, is idempotent, and writes a manifest entry for each.

| Step | Action | Notes |
| --- | --- | --- |
| 1 | Fetch GCC layers page by page (2,000 features per request, stable order by object id until a page returns fewer) | Request GeoJSON in 4326, reproject to 32644 |
| 2 | Repair geometry with ST\_MakeValid; quarantine failures in data/quarantine | Fail the build if a repair changes an area by more than 5 percent |
| 3 | Build wards, zones and the 250 m grid | Ward area must be within 5 percent of the source area field |
| 4 | DEM: mosaic tiles, resample bilinearly to 25 m on the 250 m-aligned grid, fill pits and depressions, resolve flats, compute flow direction and accumulation, slope, TWI, sink depth, HAND proxy | pysheds |
| 5 | Reduce terrain to cells: mean and 10th percentile of elevation, means of the others over 10 by 10 blocks | Percentiles damp DEM noise |
| 6 | Land cover: nearest-neighbour from 10 m to the 25 m grid, then class fractions per cell | built, tree, water fractions |
| 7 | Population: split each 100 m pixel into 2 by 2 quarter counts, sum 5 by 5 blocks per cell | Conserves ward totals; checked by test |
| 8 | Drainage: parse text attributes, build node and edge tables, compute Manning capacity, measure completeness per ward | §12.4 |
| 9 | Counts by centroid-in-cell: buildings (server-side statistics per ward), facilities, shelters; road length per cell by clipping | OSMnx graph built separately (§27) |
| 10 | Write terrain\_features and zone\_static\_features | feature\_version recorded |
| 11 | Train M1; write S per cell and S aggregates per ward | §14 |
| 12 | Compute exposure and vulnerability | §17 |

### 10.4 Terrain formulas

| Feature | Definition |
| --- | --- |
| Slope | Gradient magnitude of the 25 m DEM in degrees (NumPy gradient) |
| TWI | ln(a / tan(beta)), a = (flow accumulation cells + 1) x 25 m, beta = slope in radians clamped to at least 0.001 |
| Sink depth | Filled DEM minus original DEM; the maximum inside the cell |
| HAND proxy | Cell mean elevation minus the DEM elevation at the nearest GCC drain vertex; negative values clipped to 0. This is a proxy because true HAND follows the flow path to the nearest drainage cell |
| Distance to drain, river | Nearest-neighbour distance in metres in 32644 |
| Drain density | Drain length per square kilometre inside the cell |

### 10.5 DEM limits and mitigations

The DEM is a surface model (buildings and trees raise it) with vertical error of the same order as Chennai's relief of a few metres. Mitigations: use cell percentiles instead of point heights; use relative features (HAND proxy, sink depth, TWI) instead of absolute elevation alone; report M1 as a relative index; and keep a Phase-3 sensitivity test that perturbs the DEM by random noise and reports the rank correlation of S. The system never claims depth accuracy from the DEM.

### 10.6 Spatial quality tests

SRID is 32644 everywhere; no empty or invalid geometry; ward areas agree with the source within 5 percent; cells tile the study area without overlap; every cell has a ward; raster transforms are multiples of 25 m; population totals are conserved per ward; counts by ward equal the sum over their cells; a known sensor coordinate transforms into the expected ward.

## 11. Ingestion, Validation and Data Quality

### 11.1 Pipeline

Source, connector, validate, normalise, spatial join (flag OUTSIDE\_AOI), store (idempotent upsert, one transaction per batch), quality summary, feature builder. A connector retries three times with exponential backoff, keeps the last good data, and marks the source STALE in source\_health; it never fabricates data.

| Connector | Cadence | Notes |
| --- | --- | --- |
| gcc\_arcgis | Build time | Paged fetch; manifest hash |
| open\_meteo\_forecast | Hourly | One request for all ward centroids (comma-separated coordinates), hourly precipitation, UTC, past 1 day, forecast 2 days; fallback last good for up to 6 h flagged STALE |
| open\_meteo\_archive | On demand | Replays and antecedent rainfall |
| imd\_daily | Daily | Via imdlib; context and bias correction |
| osm | Monthly | Road graph rebuild |
| gauge\_http | 5 min | Push; device key |
| sensor\_http | 60 s | Push; device key |

### 11.2 Ingestion contracts

| Endpoint | Auth | Body | Result |
| --- | --- | --- | --- |
| POST /api/v1/data/rainfall | Service role or station key | readings array, at most 1,000: station\_id, period\_start, period\_end, depth\_mm, kind | HTTP 200 with a per-item status |
| POST /api/v1/data/water-levels | Sensor key in X-Sensor-Key, or service role | readings array, at most 1,000: sensor\_id, timestamp (ISO 8601 with offset), water\_level\_cm, optional rise\_rate\_cm\_min, battery\_percent, signal\_dbm, status, optional lat and lon | HTTP 200 with a per-item status |

Per-item status is CREATED, UPDATED, DUPLICATE\_IGNORED or REJECTED with a reason. A batch is never rejected as a whole because of one bad item. Timestamps without an offset are rejected. ### 11.3 Validation rules

| Check | Rule | Outcome |
| --- | --- | --- |
| Required fields | Present and typed | REJECTED |
| Water level range | Between -5 cm and drain depth plus 150 cm | OUT\_OF\_RANGE, quality 0 |
| Rainfall depth | 0 to 40 mm per 5 minutes | OUT\_OF\_RANGE, quality 0 |
| Missing value | null in payload | MISSING flag; stored as null, never zero (R5) |
| Future timestamp | More than 2 minutes ahead of the clock | CLOCK\_SKEW; ordering uses receive time |
| Late arrival | Rain over 15 minutes late, sensor over 10 minutes late | LATE |
| Unit sanity | Level reported in metres or rainfall in millimetres per hour caught by range checks | OUT\_OF\_RANGE |
| Outside area of interest | Point not inside any ward | OUTSIDE\_AOI; excluded from features |

### 11.4 Quality flags and score

Flags: MISSING, OUT\_OF\_RANGE, SPIKE, STUCK, LATE, CLOCK\_SKEW, REVISED, LOW\_BATTERY, WEAK\_SIGNAL, NEIGHBOUR\_DISAGREE, OUTSIDE\_AOI.

| Detector | Definition |
| --- | --- |
| SPIKE | Causal Hampel filter on the previous 5 valid readings: deviation above 3 x 1.4826 x MAD (MAD floored at 1 cm) and a step above 15 cm per minute, and no neighbouring sensor within 1.5 km rising |
| STUCK | 30 consecutive readings identical within 0.05 cm while the ward received more than 2 mm of rain in 30 minutes |
| NEIGHBOUR\_DISAGREE | Fill ratio differs from the neighbour median by more than 0.5 for more than 10 minutes |
| LOW\_BATTERY, WEAK\_SIGNAL | Battery below 15 percent; signal below -105 dBm |

Quality per reading: 1.0 by default; 0 for OUT\_OF\_RANGE, SPIKE or STUCK; multiplied by 0.6 for LOW\_BATTERY or WEAK\_SIGNAL, by 0.7 for NEIGHBOUR\_DISAGREE, by 0.8 for LATE (all ASSUMED). A reading with quality 0 is stored for audit and never used in features.

### 11.5 Freshness limits

| Source | Soft age (confidence decay time constant) | Hard limit (treated as missing) |
| --- | --- | --- |
| Rain observation | 20 min | 60 min |
| Rain forecast | 120 min | 3 h (persistence only beyond) |
| Water-level sensor | 5 min | 15 min |

### 11.6 The simulator is a client

The sensor and gauge simulator (§12) runs as a separate process and posts through the same endpoints with per-device keys. It cannot write to the database directly. Replacing it with a real gateway changes no server code. Faults (dropout, outage, stuck, spike, drift, battery decay, clock skew) are injected at the device, so the validators and quality score are exercised by the real path.

## 12. Hydrology and Sensor Simulation

### 12.1 Purpose and status

The hydrology module is a transparent, millisecond-fast model with three jobs: generate simulated sensor readings, provide a physically motivated drain-stress feature when sensors are unavailable, and generate training storms for M2. It is PROTOTYPE and ASSUMED throughout. It is not a validated SWMM or HEC-RAS replacement, and nothing computed by it is presented as an observed or validated inundation.

### 12.2 Equations

| Component | Equation | Symbols |
| --- | --- | --- |
| SCS-CN runoff | Q = (P - Ia)^2 / (P - Ia + S) for P > Ia, else 0; S = 25400 / CN - 254 (mm); Ia = lambda x S | P cumulative rainfall (mm), Q cumulative runoff (mm), lambda = 0.2 (configurable; lower values suit urban surfaces) |
| Curve number prior | CN = 60 + 38 x built\_fraction (ASSUMED) | built\_fraction in \[0, 1\]; CN from 60 to 98 |
| Runoff rate | q(t) = Q(t) - Q(t-1) per minute | mm per minute |
| Lagged inflow | i(t) = kappa x q(t - L) | kappa in cm per mm (site sensitivity), L lag in minutes |
| Linear reservoir with outflow | h(t+1) = h(t) + i(t) - k x h(t) x (1 - b) x tide(t) | h level (cm), k outflow coefficient per minute, b blockage in \[0, 1\] |
| Tide factor | tide(t) = 1 - A x max(0, sin(2 pi t / 12.42 h + phase)) | A tidal backwater amplitude (0 inland) |
| Overflow ponding | If h exceeds drain depth: pond += h - depth, h = depth; pond decays by 2 percent per minute; reported level = h + pond | Overflow minutes set sim\_flooded = true (ground truth) |
| Manning full-flow capacity | Qcap = (1 / n) x A x R^(2/3) x s^(1/2) | A = w x d, wetted perimeter P = w + 2d (open) or 2(w + d) (covered), R = A / P, s = (invert start - invert end) / length clamped to at least 0.0005, n = 0.015 (concrete, ASSUMED) |

Any missing or non-positive input leaves the edge capacity null and attrs\_complete false; a ward's drain capacity index is the percentile rank across wards of (sum of Qcap over complete edges per km²) multiplied by the complete fraction of drain length. It ranks wards; it is not a design calculation.

### 12.3 Model-based drain stress

Used only when no valid sensor covers a ward (substitution mode, flagged uses\_substitute\_inputs).

rho = c\_w x i / (i\_design x (1 - b\_ward)) x g\_w, with c\_w = 0.15 + 0.75 x built\_fraction, i the highest 15-minute intensity (mm per hour) in the hour ending at the horizon, i\_design = 50 mm per hour, b\_ward = 0.15 (plus 0.2 where the GCC obstacles field is non-empty), g\_w = 1.5 - drain capacity index (so poorly drained wards get g near 1.5). The feature is D\_est = ramp(rho; 0.6, 1.2). All constants are ASSUMED and live in config/risk.yaml.

### 12.4 Rainfall timeline

Observed rainfall is stored as 15-minute bins (gauges, or hourly reanalysis spread uniformly). For lead time tau the blended intensity is rain\_hat(tau) = w(tau) x persistence + (1 - w(tau)) x nwp(tau), with w(tau) = exp(-tau / 45 min), persistence the exponentially weighted mean of the last 30 minutes (half-life 20 minutes) and nwp the hourly forecast spread uniformly over 15-minute bins. Forecast scenarios multiply the forecast part by 0.7, 1.0 and 1.4. The weights are ASSUMED; no radar nowcast is built.

### 12.5 Simulator engine

| Aspect | Specification |
| --- | --- |
| Determinism | numpy default\_rng(seed); the same scenario and seed give identical output |
| Clock | Simulated clock with a speed factor (default 120x); stored in sim\_runs.sim\_clock; all components read it through the clock service |
| Sensors | 48 by default: one per GCC zone plus three per demo ward; placed on drain edges; depth from the GCC attribute, else a class default flagged ASSUMED; warning at 60 percent and critical at 85 percent of depth (ASSUMED) |
| Per-sensor draws | kappa uniform 0.4 to 1.6 cm per mm; lag uniform 5 to 25 min; k uniform 0.01 to 0.04 per minute; blockage Beta(2, 10) plus 0.2 where GCC obstacles exist; spatial rain factor lognormal sigma 0.1 per storm |
| Hero sensors | A scenario may pin parameters; DEMO-STORM-01 pins kappa 3.4, lag 8, k 0.02, b 0.15 (tuned so the scripted storm produces a demonstration timeline; not calibrated to real drains) |
| Baseline | 0 to 5 cm with 0.5 cm noise, 0.1 cm quantisation and slow drift |
| Faults | Markov dropout (entry 0.003 per minute, mean burst 5 min); zone outage 5 to 20 min; stuck; spikes (p 0.002, plus or minus 30 to 80 cm); drift plus or minus 2 cm per hour; battery 60 to 100 percent draining 0.01 to 0.03 percent per hour (below 15 percent dropout x3, at 0 offline); signal random walk -60 to -110 dBm; clock skew 1 to 3 min |
| Ground truth | sim\_flooded per ward per minute, used only by the learning harness, never by the analysis graph |
| Interface | Posts to the production endpoints with per-device keys (§11.6) |

### 12.6 Training storms for M2

About 300 synthetic storms (triangular and bimodal hyetographs, peak 10 to 120 mm per hour, duration 1 to 10 hours) plus about 10 historical replay windows scaled 0.5 to 1.5, run on 48 sensors at 5-minute sampling, give about one million rows. Splits are by storm: 60 percent train, 20 percent validation, 20 percent test; a second test set is a domain-shift set (kappa, k and lag perturbed by 30 percent, new seeds, faults on). All resulting metrics are SYNTHETIC-VALIDATION.

### 12.7 Reference run

For DEMO-STORM-01 (§43.1) with built fraction 0.80, CN = 90.4, S = 27.0 mm, Ia = 5.4 mm; 60 mm of rain produces 36.6 mm of runoff and 100 mm produces 73.6 mm. The hero sensor (depth 100 cm) reaches 60 cm at T+30 min, 85 cm at T+40 min and overflows at T+49 min (seed 42, reference implementation).

### 12.8 Simulator tests

Mass balance (with k = 0, level equals cumulative inflow); monotonicity (more rain never lowers the peak level); determinism (identical output for identical seed); fault exercise (every fault type produces the matching QC flag); API parity (simulator output passes the same validators as a hand-written device payload).

## 13. Feature Engineering

### 13.1 Principles

Features are computed as of the analysis time t using windows (t - w, t\]; the same function serves training and serving; missing is null, not zero (a window with more than 20 percent missing sub-intervals returns null with MISSING\_RAIN); sensor forward-fill is allowed for at most 3 minutes (FFILL) and then null. feature\_version is the first 12 hex characters of SHA-256 over the code version, features.yaml and input manifest hashes. Every run writes runs/\<run\_id>/features.parquet and stores its hash as an evidence item.

### 13.2 Catalogue

| Group | Features | Definition | Used by |
| --- | --- | --- | --- |
| Rainfall | r15, r60, r180 | Accumulation (mm) over the 15, 60 and 180 minutes ending at t (or at t + tau for a horizon, using the blended timeline) | M2, M3 |
| Rainfall | rain\_hr\_eq | max(r60, 4 x r15), the hourly-equivalent intensity | M3, floor F3 |
| Rainfall | a72 | Observed rainfall in (t - 72 h, t - 3 h\] | M3 |
| Forecast rain | f15, f60, f120 | Forecast accumulation over the next 15, 60 and 120 minutes | M2 |
| Sensor | level\_cm, fill\_ratio | Latest valid level; level divided by drain depth | M2, M3 |
| Sensor | rise\_5, rise\_10, rise\_15, accel | Least-squares slope over the last 5, 10 and 15 minutes (cm per minute); accel = rise\_5 minus rise\_5 five minutes earlier | M2, M3 |
| Sensor | t\_full\_min | (depth - level) / rise when rise is positive, else null | Display, evidence |
| Ward sensor aggregate | n\_valid, phi\_max, rise\_max, q\_top | Over valid sensors in the ward, plus neighbours within 1.5 km if the ward has none (flag NEIGHBOUR\_SENSOR) | M3, confidence |
| Static | elevation, slope, TWI, sink depth, HAND proxy, distances, built fraction, drain capacity index | §10.4 | M1, M3 |
| Susceptibility | S\_cell, S\_mean, S\_p90, S\_w | S\_w = 0.5 x S\_mean + 0.5 x S\_p90 | M3, footprint |
| Impact | exposure E, vulnerability V | §17 | Policy |
| Site | CN, drain depth, built fraction, capacity proxy | §12 | M2 |
| Tide | sin and cos of tidal phase | Simulated tide | M2 |

Historical flood frequency is a ward-level prior stored for display and similar-event retrieval; it is not an input to M1 and is not used by M3.

### 13.3 Horizon features

For horizon tau in {15, 30, 60, 120}, rainfall features use the blended timeline ending at t + tau; sensor features at the horizon come from M2 (P10, P50, P90 level divided by depth) or from the linear fallback; rise at the horizon is the slope implied by consecutive M2 horizons or, in fallback mode, the current ten-minute slope held constant. Horizon 0 uses current observations only.

### 13.4 Parity test

A test builds features for a stored (ward, time) once through the training path and once through the serving path and requires identical values and identical feature\_version.

## 14. M1 — Flood Susceptibility Model

### 14.1 Purpose and output

M1 ranks 250 m cells by how prone their terrain and drainage setting is to flooding. It is static (retrained rarely) and produces S, a relative susceptibility index in \[0, 1\] that is the percentile rank of the model score across the study area. S is not a probability and is never displayed as one.

### 14.2 Labels

Positives: cells containing at least one inundation point (OpenCity inundation points with depth, 2015 flooding points) or intersecting an observed flood polygon. Negatives (pseudo-absences): cells at least 750 m from any positive and outside the GCC High hazard zone. The GCC hazard zones and return-period layers are MODELLED, so they serve as an exclusion mask and an independent check, not as positive labels. Because labels are presence-only, every report that shows M1 says so. M1 is built only if at least 150 positive cells exist; otherwise the fixed-weight fallback index is used and labelled.

### 14.3 Features

elev\_mean, elev\_p10, slope\_deg, twi, flow\_acc\_log, sink\_depth\_m, hand\_m, dist\_drain\_m, dist\_river\_m, built\_frac, drain\_density, drain\_capacity\_proxy (nullable). Excluded: historical flood frequency (derived from the labels), population and shelter features (not terrain).

### 14.4 Model

LightGBM binary classifier: num\_leaves 15, min\_data\_in\_leaf 40, learning\_rate 0.05, up to 500 trees with early stopping after 50, feature\_fraction 0.8, bagging\_fraction 0.8, lambda\_l2 5, positives to negatives sampled 1 to 5, fixed seeds. Monotone constraints encode physical priors (higher elevation and higher HAND lower susceptibility; deeper sinks raise it). Baselines: logistic regression and the fixed-weight index.

### 14.5 Validation

Buffered spatial block cross-validation: 5 km blocks, 5 folds, cells within 500 m of a test block removed from training; leave-one-event-out when at least two independent events exist. Metrics: ROC-AUC, PR-AUC, Brier score, Continuous Boyce Index (appropriate for presence-only data). Independent checks: share of top-decile cells inside the GCC High and Moderate hazard zones compared with the share expected by chance; rank stability of S under DEM noise (§10.5). The result is described as spatial cross-validation on incomplete labels and is never called validated.

### 14.6 Output and fallback

S\_cell is written to terrain\_features; ward aggregates S\_mean, S\_p90 and S\_w to zone\_static\_features. TreeSHAP (path-dependent) on the trained model produces an offline global importance and per-cell maps for the report. Fixed-weight fallback index (ASSUMED): low elevation 0.25, low HAND 0.20, sink depth 0.15, TWI 0.10, built fraction 0.10, inverse drain proximity 0.10, inverse drain density 0.10.

### 14.7 Acceptance targets (to be measured, not claimed)

Spatial-CV ROC-AUC at least 0.70; Continuous Boyce Index at least 0.5; top-decile overlap with hazard zones at least twice the chance rate; Spearman rank correlation of S under DEM noise at least 0.8. If a target is missed, the report says so and the fallback index stays available.

## 15. M2 — Water-Level Forecasting Model

### 15.1 Purpose

M2 forecasts the water level in a monitored drain at +15, +30, +60 and +120 minutes with a P10, P50 and P90 band. It works per sensor; the Risk agent aggregates sensors to the ward (§15.8). In the MVP it is trained on simulated storms, so every skill number is SYNTHETIC-VALIDATION.

### 15.2 Target and architecture

Target: delta h = level(t + tau) - level(t) for tau in {15, 30, 60, 120}. One LightGBM regressor per (tau, quantile) with objective quantile and alpha 0.1, 0.5 and 0.9: 12 boosters in one registry bundle. Predicted level = level(t) + delta h, clipped to \[0, drain depth + 100 cm\]. Quantile crossings are repaired by sorting the three outputs. Predicting the change rather than the level removes the trivial autoregressive component and makes skill against persistence measurable.

### 15.3 Inputs

Level lags at 1, 5, 10, 15, 30 and 60 minutes; rise\_5, rise\_10, rise\_15 and accel; observed rain sums over 5, 15, 30, 60 and 180 minutes; forecast rain sums over the next 15, 30, 60 and 120 minutes; minutes since rain onset; site features (CN, drain depth, S\_w, built fraction, capacity proxy); tide phase. Missing sensor history shorter than 10 valid minutes produces no forecast (§15.9).

### 15.4 Baselines and metrics

| Baseline | Definition |
| --- | --- |
| Persistence | level(t + tau) = level(t) |
| Linear extrapolation | level(t) + rise\_10 x tau, clipped; also the production fallback |
| Ridge, random forest | Reference learners on the same features |

Metrics per horizon: MAE and RMSE of the P50 level; skill score SS = 1 - RMSE\_model / RMSE\_persistence; pinball loss at the three quantiles; coverage of the P10 to P90 band (nominal 0.80) and its mean width; peak-level error and peak-timing error; time-to-threshold error; and, for the event 'level reaches the warning threshold within 30 minutes', F1 and median lead time. MAPE is reported only for peaks above 20 cm.

### 15.5 Promotion and horizon gating

A candidate bundle may become ACTIVE only if, on the domain-shift test set and for each horizon it enables: SS is above 0 against persistence and against linear extrapolation; RMSE is not more than 5 percent worse than the current ACTIVE bundle; and P10 to P90 coverage lies between 0.70 and 0.90. A horizon that fails is disabled in the bundle manifest and returns method DISABLED with the reason; the UI shows 'not skilful at this horizon' instead of a number.

### 15.6 Fallback and extrapolation flags

If the bundle is missing, a hash check fails, or a horizon is disabled, the linear extrapolation runs and rows are marked method LINEAR\_FALLBACK. If any input lies outside the 1st to 99th percentile of the training data, the forecast is marked extrapolated and the confidence calculation treats the interval as wider (§19).

### 15.7 Deep-learning experiment gate

A GRU or LSTM stays in a notebook. It is considered for the pipeline only after at least six months of real telemetry from at least twenty sensors exist and the network beats the LightGBM bundle by at least 10 percent RMSE on held-out real storms.

### 15.8 Ward aggregation

For each ward, the Risk agent takes the valid sensor (own ward first, then neighbours within 1.5 km) with the highest P50 fill ratio at each horizon and propagates its P10 and P90; it records the sensor id, the number of sensors used and any substitution flag in the assessment evidence.

### 15.9 Failure modes

Fewer than 10 valid minutes of history, a stuck or spiking sensor, or a missing model each produce an explicit method and reason (DISABLED, LINEAR\_FALLBACK) in water\_level\_forecasts; the Risk agent then uses the model-based drain stress (§12.3) or reports INSUFFICIENT\_EVIDENCE for that ward.

## 16. M3 — Calibrated Flood Hazard Model

### 16.1 Definition

M3 turns evidence about rainfall, drain state and terrain into a flood-hazard index H in \[0, 1\] per ward and horizon: z = b0 + sum over features of w\_k x f\_k, and H = sigmoid((z - b) / T). The parameters b and T are calibration parameters, 0 and 1 until a calibration is fitted. Every f\_k is a ramp-normalised feature in \[0, 1\], where ramp(x; lo, hi) = clip((x - lo) / (hi - lo), 0, 1).

### 16.2 Features, ramps and prior weights

| Feature key | Quantity | Ramp (lo, hi) | Prior weight |
| --- | --- | --- | --- |
| rain\_intensity | rain\_hr\_eq at the horizon (mm per hour) | 20, 100 | 2.4 |
| rain\_accumulation | r180 at the horizon (mm) | 40, 200 | 1.8 |
| antecedent | a72 (mm) | 30, 150 | 0.6 |
| water\_level | fill ratio at the horizon | 0.40, 1.00 | 3.0 |
| level\_rise | rise in cm per minute | 0.2, 2.0 | 1.4 |
| drain\_stress\_model | rho (§12.3), substitution mode only | 0.6, 1.2 | 1.8 |
| susceptibility | S\_w | none (already in \[0, 1\]) | 1.6 |
| Intercept b0 |  |  | -6.0 |

All weights and ramp bounds are ASSUMED engineering priors, labelled PROTOTYPE, and stored in config/risk.yaml. Every weight is non-negative, so H never falls when any input rises; a property test enforces this. Water level and rise carry the largest weights because they are direct evidence of drain saturation; rainfall and susceptibility give anticipatory evidence.

### 16.3 Sanity fixtures (golden tests)

| Case | Inputs | H | Band |
| --- | --- | --- | --- |
| Dry day, very susceptible, dense and vulnerable ward | no rain, level 0, S = 0.9 | 0.0104 | 0 (LOW) |
| Heavy rain, good drainage, calm sensors | rain\_hr\_eq 100, r180 60, a72 20, fill 0.10, rise 0, S = 0.3 | 0.052 | 0 (LOW) |
| Low rain, drain nearly full (blockage or backwater) | rain\_hr\_eq 5, r180 10, a72 10, fill 0.95, rise 0.1, S = 0.6 | 0.092 | 0 (LOW), then safety floor F1 raises it to HIGH (§18.4) |
| Everything at its maximum | rain 150, r180 250, a72 200, fill 1.0, rise 3.0, S = 1.0 | 0.9918 | 3 |

These values were computed with the reference implementation (§42) and are the first unit tests of the risk package.

### 16.4 Sensor-substitution mode

When a ward has no valid sensor (own or neighbour) at the horizon, water\_level and level\_rise are removed and drain\_stress\_model is used in their place. The assessment is flagged uses\_substitute\_inputs, the data-quality term of the confidence drops (§19), and the substitution is listed in the evidence. In the reference run at T+20 the sensor-based H(+30) of 0.80 would become 0.23 in substitution mode, which is why the hold rule in §18.5 exists.

### 16.5 Horizons and the scenario envelope

H is evaluated at horizons 0, 15, 30, 60 and 120 minutes. The interval \[H\_low, H\_high\] is a scenario envelope, not a statistical confidence interval: H\_low uses forecast rain multiplied by 0.7 and the M2 P10 level (or ten-minute rise multiplied by 0.7 in fallback mode); H\_high uses rain multiplied by 1.4 and P90 (rise multiplied by 1.3). Its width enters the confidence term (§19).

### 16.6 Time to impact

With the onset threshold H = 0.60 (configurable), time to impact is the earliest horizon at which H reaches 0.60, interpolated linearly between adjacent horizons and labelled 'interpolated'. If H(0) is already at least 0.60 the time to impact is 0. If no horizon within 120 minutes reaches the threshold the field is null.

### 16.7 Calibration

| Status | Meaning | How reached |
| --- | --- | --- |
| UNCALIBRATED | Prior weights, b = 0, T = 1 | Initial state |
| SYNTHETIC\_CALIBRATED | Fitted on simulator ground truth | Offline job on simulated outcomes |
| HINDCAST\_CALIBRATED | Fitted on real historical event labels | Offline job on D12 events |
| OUTCOME\_CALIBRATED | Fitted on recorded operational outcomes | Controlled learning (§34) |

Default method: two-parameter logit recalibration, H = sigmoid((z - b) / T), with b and ln T fitted by minimising log-loss with a small L2 penalty, using out-of-fold predictions. With fewer than 50 outcome-paired ward-horizons, only the intercept b is fitted so that the mean predicted probability matches the observed event rate (prior-shift correction), and T stays 1. Isotonic regression is allowed only after at least 500 pairs including 50 positives. Every calibration is reported with a five-bin reliability table and the expected calibration error, and is stored as a CANDIDATE model\_versions row; promotion needs a human (§34).

Display rule (R9): while calibration status is UNCALIBRATED the UI says 'flood likelihood index' and never 'probability'; after calibration it says 'estimated probability, calibrated on N events (status)'.

### 16.8 Worked computation

Reference run, hero ward, analysis at T+20 min, horizon +30 min: rain\_hr\_eq is 66 mm per hour, giving f = 0.58; r180 is 72 mm, giving 0.20; a72 is 18 mm, below the ramp start, giving 0; the linear-fallback level forecast is above the drain depth, giving fill ratio 1.0 and f = 1.0; the ten-minute rise of 2.7 cm per minute gives f = 1.0; S\_w = 0.78. Then z = -6.0 + 2.4 x 0.58 + 1.8 x 0.20 + 0.6 x 0 + 3.0 x 1.0 + 1.4 x 1.0 + 1.6 x 0.78 = 1.40, so H = sigmoid(1.40) = 0.80 (scenario envelope 0.55 to 0.87). The ward falls in band 3, which permits HIGH or VERY\_HIGH (§18).

## 17. Exposure, Vulnerability and Impact

### 17.1 Four separate quantities

| Quantity | Question it answers | Source | Changes with time |
| --- | --- | --- | --- |
| Hazard H | How likely is flooding at this ward and horizon | M3 (§16) | Every cycle |
| Exposure E | How much is in the way if it floods | Counts over susceptible cells | Static, rebuilt with the data |
| Vulnerability V | How badly and how persistently people are affected | Demographics, shelter distance, evacuation difficulty | Static |
| Impact I | Combined consequence class | I = 0.6 E + 0.4 V | Static |

The separation is deliberate: hazard says whether the event may happen; impact says how much it would matter. Impact never enters H and can only select a level inside the band that hazard permits (§18).

### 17.2 Exposure

For each ward, count over its susceptible cells only (S\_cell at least 0.70, so the top 30 percent most susceptible cells of the study area; ASSUMED): population, buildings, road length, hospitals and clinics, schools and other critical facilities. Each count is converted to a percentile rank across wards, rank01, and E = 0.35 rank01(population) + 0.15 rank01(buildings) + 0.15 rank01(road km) + 0.15 rank01(hospitals and clinics) + 0.10 rank01(schools) + 0.10 rank01(other critical facilities). A missing component is dropped, the others are renormalised, and the coverage is stored.

### 17.3 Vulnerability

V = 0.5 rank01(share of population aged 0 to 4 or 65 and over) + 0.3 rank01(distance from the ward centroid to the nearest official shelter, larger is worse) + 0.2 rank01(evacuation difficulty), where evacuation difficulty = 1 - min(1, road density / the 90th percentile of ward road density). Missing components are renormalised and flagged. All weights are ASSUMED and PROTOTYPE.

### 17.4 Dynamic impact estimate and footprint

The indicative footprint of a ward at hazard H is the set of its cells with S\_cell at least s\*, where s\* = clip(0.90 - 0.60 H, 0.30, 0.90). It is drawn as 250 m blocks and described as an 'indicative flood-prone area', never as an inundation depth. The impact estimate counts people, buildings, facilities (hospitals, schools), subways and road kilometres inside the footprint with PostGIS and stores them as impact\_estimate; the numbers inherit the label MODELLED. Overlap with observed layers is measured at cell level (IoU, precision, recall) only when an outcome exists.

### 17.5 Limits

Population is a static modelled layer (WorldPop), not occupancy; facility lists are as complete as OpenStreetMap; shelter capacity is unknown (R11); ranks are relative to the study area, so a ward's E can change when other wards change.

## 18. Risk Classification Policy

### 18.1 Pipeline

For each horizon: H, then hazard band, then the impact threshold selects the level inside the band, then safety floors. The assessed level is the maximum over the actionable horizons 0, 15, 30 and 60 minutes. Hold and hysteresis rules then apply, confidence governs the review rules, and the level maps to an alert severity. The +120 minute horizon never sets the level; it can only raise a watch flag.

### 18.2 Bands and the hazard-gated matrix

| Hazard band | H range | Permitted levels | Level if I is below 0.50 | Level if I is at least 0.50 |
| --- | --- | --- | --- | --- |
| 0 | below 0.10 | LOW only | LOW | LOW |
| 1 | 0.10 to below 0.40 | LOW or MEDIUM | LOW | MEDIUM |
| 2 | 0.40 to below 0.70 | MEDIUM or HIGH | MEDIUM | HIGH |
| 3 | 0.70 and above | HIGH or VERY\_HIGH | HIGH | VERY\_HIGH |

Cut points (0.10, 0.40, 0.70) and the impact threshold (0.50 per band) are PROTOTYPE values in config/risk.yaml. Exposure and vulnerability cannot lift a ward above the pair its hazard band permits, and a ward in band 0 is LOW whatever its impact (R10).

### 18.3 Watch flag

If H at +120 minutes is in band 2 or above and the assessed level is below HIGH, the assessment carries watch\_outlook = true. The UI shows a WATCH badge and the operator console lists the ward; no alert is drafted from the watch flag alone.

### 18.4 Deterministic safety floors

Floors raise the level above what the band permits. They use hazard evidence only (never exposure), they require valid readings (quality above 0, not STALE), and each is recorded in floor\_applied with its evidence ids.

| Floor | Condition | Minimum level |
| --- | --- | --- |
| F1 sensor near overflow | Any valid ward or neighbour sensor at fill ratio 0.85 or higher (the critical threshold) | HIGH |
| F2 rapid rise | Valid sensor at fill ratio 0.60 or higher and rise at least 0.5 cm per minute | MEDIUM |
| F3 extreme rain | rain\_hr\_eq at the current time at least 100 mm per hour | MEDIUM |

A floor can never produce VERY\_HIGH. The fixture in §16.3 (low rain, drain nearly full) is HIGH because of F1 even though H is 0.09.

### 18.5 Data-loss hold and de-escalation

Data loss never lowers a level by itself. If a ward was HIGH or VERY\_HIGH in the previous cycle and its sensors or rainfall become invalid, the previous level is held for 30 minutes with hold\_applied = SENSOR\_LOSS\_HOLD, a REQUEST\_HUMAN\_ASSESSMENT recommendation is created, and the ward stays in the review queue. De-escalation is gradual: escalation is immediate, but the level may fall by at most one step per cycle and only after the lower level has persisted for two consecutive cycles spanning at least 20 minutes.

### 18.6 Confidence as a governance gate

Confidence C (§19) never changes H or the level, so uncertainty cannot be turned into false reassurance. It governs process:

| Condition | Effect |
| --- | --- |
| C at least 0.70 (HIGH) | Normal pathway |
| C 0.40 to 0.70 (MEDIUM) | Reviewer checklist adds 'uncertainty acknowledged' |
| C below 0.40 (LOW) | LOW-CONFIDENCE tag on the alert; no resource-deployment actions drafted; VERY\_HIGH drafts REQUEST\_HUMAN\_ASSESSMENT instead of EVACUATION\_RECOMMENDATION |
| C below 0.25, or required inputs missing | INSUFFICIENT\_EVIDENCE: no level is computed |

### 18.7 Severity mapping and approvers

| Level | Alert severity | Public alert | Approver role |
| --- | --- | --- | --- |
| LOW | none | No | Not applicable |
| MEDIUM | ADVISORY | No; internal notice on the municipal dashboard | Municipal operator |
| HIGH | WARNING | Yes, after approval | Emergency coordinator |
| VERY\_HIGH | URGENT | Yes, after approval | Emergency coordinator |

### 18.8 Continuous index

R = H x (0.5 + 0.5 I) is a continuous index used only to order wards and to shade the map within a level. It never decides the level.

### 18.9 Worked classification (reference run, T+20 min)

Hero ward (I = 0.75): H(0) = 0.22 gives band 1 and MEDIUM; H(+15) = 0.51 gives band 2 and HIGH; H(+30) = 0.80 gives band 3 and VERY\_HIGH; H(+60) = 0.68 gives band 2 and HIGH; no floor applies. Assessed level: VERY\_HIGH. Time to impact 19.6 minutes (interpolated). H(+120) = 0.53, band 2, so the watch flag is also set. Confidence 0.53 (MEDIUM), so VERY\_HIGH is permitted with the uncertainty acknowledgement. Severity URGENT; approver: emergency coordinator. Contrast ward (I = 0.39) under the same rain stays band 0 at every horizon and is LOW.

### 18.10 Policy tests

Band and matrix table-driven tests; property test that raising E or V never changes the band; floor tests (F1 to F3 with valid, stale and flagged inputs); hold test (sensors vanish at HIGH, level stays HIGH for 30 minutes); hysteresis test (no drop of more than one step per cycle); confidence-gate tests; golden tests for the fixtures in §16.3.

## 19. Uncertainty, Confidence and Abstention

### 19.1 Kinds of uncertainty and how each is shown

| Kind | Representation |
| --- | --- |
| Data quality and freshness | Data-quality term q (§19.2) |
| Model and scenario spread | Envelope \[H\_low, H\_high\] and its width |
| Extrapolation | extrapolated flag and widened interval |
| Evidence agreement | Agreement factor a\_ev |
| Calibration | calibration\_status and the index-versus-probability wording |

### 19.2 Confidence

q = min(q\_cov, q\_fresh, q\_valid). q\_cov = 0.5 x rain\_ok + 0.5 x sensor\_cov, where sensor\_cov = min(1, n\_valid / 2) and is fixed at 0.4 in substitution mode. q\_fresh = the minimum over used sources of exp(-age / tau), with tau 20 minutes for rain observations, 120 minutes for forecasts and 5 minutes for sensors. q\_valid = 1 - (flagged readings used in the last 15 minutes) / (readings in the last 15 minutes). w\_int = H\_high - H\_low. a\_ev = 1.0 when rain and sensor evidence agree or are both low, 0.8 when only one type is available, 0.6 when they conflict (normalised signals differ by more than 0.5 and one is at least 0.6).

C = q x (1 - min(1, w\_int)) x a\_ev. It is a heuristic score, not a probability; classes are HIGH at 0.70 or more, MEDIUM from 0.40, LOW below 0.40 (all ASSUMED).

### 19.3 Abstention

The system returns INSUFFICIENT\_EVIDENCE for a ward when q is below 0.25, when required static features are missing, or when neither a valid rainfall source nor a valid sensor exists. The record states the reason in plain words ('rainfall data unavailable since 03:40'); it never carries a level, and the map shows the ward hatched grey, never green.

### 19.4 Worked example (reference run, T+20 min)

Rain observation age 5 minutes gives exp(-0.25) = 0.78; sensor age 1 minute gives exp(-0.2) = 0.82; forecast age 30 minutes gives exp(-0.25) = 0.78; q = 0.78. The envelope is 0.55 to 0.87, so w\_int = 0.32; evidence agrees, so a\_ev = 1. C = 0.78 x 0.68 x 1 = 0.53, which is MEDIUM.

### 19.5 Display rules

Every risk widget shows the interval, the confidence class, the age of the oldest input, the calibration wording, and a SIMULATED badge whenever uses\_simulated\_inputs is true. No widget uses the word 'safe'; a LOW ward reads 'no elevated risk assessed' with the time and data age.

## 20. Explainability and Root-Cause Analysis

### 20.1 Principles

An explanation states which inputs drove this assessment according to the model and policy computation. It does not claim physical causation. Every statement cites evidence ids that resolve to stored values; the method and baseline are always shown.

### 20.2 Methods

| Target | Method | Players and baseline | Label |
| --- | --- | --- | --- |
| Ward risk index (M3 plus impact) | Exact Shapley values by enumeration of all 2^n coalitions | Up to 8 driver groups: rain\_intensity, rain\_accumulation, antecedent, water\_level, level\_rise, susceptibility, exposure, vulnerability (drain\_stress\_model replaces the two sensor groups in substitution mode). Value function v(C) = H x (0.5 + 0.5 I) with absent players at baseline: dynamic drivers 0, S, E and V at the study-area median. Efficiency holds: the values sum to v(actual) minus v(baseline) | EXACT (Shapley, risk index) |
| Log-odds of M3 | Closed form: w\_k x (f\_k - f\_k,baseline) | Same baseline | EXACT (linear in z) |
| M1 susceptibility | TreeSHAP, path-dependent | Training data | TreeSHAP (offline report) |
| M2 forecast | TreeSHAP on the P50 booster for one sensor and horizon, top 5 features, on demand | Training data | TreeSHAP (drill-down) |
| More than 12 players | Permutation sampling, 200 permutations, standard error reported | As above | APPROXIMATE (never called exact) |
| Time budget exceeded (200 ms) | One-at-a-time ablation against the baseline | As above | ABLATION |

With eight players the exact computation needs 256 evaluations of a closed-form function, so it is cheap and always used for the ward assessment. A positive value increases the risk index relative to the baseline; contribution\_pct is a positive value divided by the sum of positive values; negative values are shown as mitigating factors.

### 20.3 Reading the baseline

The UI states the baseline in one sentence: 'compared with a dry ward of median susceptibility, exposure and vulnerability'. Because the risk index multiplies hazard by impact, exposure and vulnerability receive small values when hazard is low, which is the intended behaviour of hazard gating.

### 20.4 Evidence registry

Every value that enters a calculation is registered as an evidence\_items row with an id of the form EV-\<TYPE>-\<WARD>-\<UTC timestamp>-<8 hex of the content hash>: rainfall windows, sensor readings with their QC flags, static feature snapshots, model outputs, the config hash, the feature file hash and the retrieved analog events. A factor in risk\_factors lists the evidence ids that support it.

### 20.5 What an explanation contains

| Part | Content |
| --- | --- |
| Where | Ward and, if available, the cells and sensors most responsible |
| When | Time to impact (interpolated), the horizon at which the level is reached |
| Why | Ranked factors with contribution percentages, direction, value and evidence ids; the method label |
| What if | H under the 0.7 and 1.4 rainfall scenarios (the envelope) |
| Similar events | The three closest historical events by standardised Euclidean distance over max 1 h, 3 h and 24 h rainfall, a72 and S\_w, similarity = 1 / (1 + distance), each with the flooded fraction of the ward; the text says how many events were available and says so if fewer than three |
| Recommended actions | From the decision engine (§26), with the policy version |

### 20.6 Narrative

Template mode renders the parts above into fixed sentences. LLM mode may paraphrase them (§24). In both modes a validator checks that cited evidence ids exist for the same run and ward, that every number in the text equals a supplied fact at the displayed precision, and that no instruction wording appears outside approved templates. A failed validation falls back to the template and is logged.

### 20.7 Tests

Shapley efficiency (sum equals v(actual) minus v(baseline) within 1e-9); evidence-id resolution; template completeness for every factor; a narrative with an invented number is rejected; the method label is present on every attribution row.

## 21. Multi-Agent Architecture

### 21.1 Agent roster

An agent is a Python class with a typed run() that returns an AgentResponse. Agents read and write only through typed tool wrappers (aquarizz.tools) and a run-scoped context persisted in agent\_runs.trace. They never fabricate or silently substitute inputs, and they list every missing input. No language model decides control flow.

| Agent | Mission | Allowed | Forbidden | Abstains when |
| --- | --- | --- | --- | --- |
| Orchestrator | Control the run: plan, route, retry, escalate | Choose the next node by rule; retry a failed node once; skip nodes when no ward is MEDIUM or above; use fallbacks; route to human review | Compute numbers; approve; dispatch; bypass policy; use an LLM for routing | No valid rainfall source and no valid sensor for any ward |
| Data & Retrieval | Assemble the evidence bundle per ward | Read the database; one fallback refresh of a connector; run QC; build the feature file | Fill gaps with invented or interpolated values | A ward has neither valid rainfall nor a valid sensor |
| Forecasting | Blended rainfall timeline and water-level forecasts with intervals | Run M2; use the linear fallback; flag extrapolation | Hide a missing model; claim skill for a disabled horizon | Never abstains; returns null forecasts with reasons |
| Flood Risk Analysis | H per horizon, E, V, impact, level, floors, confidence, time to impact, footprint | Evaluate M3 and the policy; run the scenario envelope | Alter weights or thresholds; let confidence change the level | q below 0.25 or required static features missing |
| RCA & Explanation | Attribution, evidence registry, similar events, narrative | Exact Shapley; TreeSHAP drill-down; template or validated LLM narrative | Add facts, numbers or ids; recommend actions | Fewer than two factors backed by evidence |
| Decision & Recommendation | Recommendations, shelters, candidate routes, alert draft | Apply policy rules; plan routes; draft from approved templates | Dispatch; approve; change risk; invent shelters or capacities; write free-text safety instructions | Explanation unavailable |

### 21.2 Services that are not agents

| Service | Role | Why it is not an agent |
| --- | --- | --- |
| Human oversight | Review queue, approval transitions, audit | Authority belongs to people and the database, not to an agent |
| Dispatcher | Sends approved alerts; own database role | Must hold credentials agents cannot reach |
| Learning | Outcome pairing, metrics, calibration candidates | Runs offline and never promotes |

### 21.3 Typed tool wrappers

| Tool | Reads | Writes | Used by |
| --- | --- | --- | --- |
| get\_rain\_timeline, get\_sensor\_window, get\_static\_features | Observation and static tables | None | Data & Retrieval |
| refresh\_forecast\_once | Open-Meteo | rainfall\_forecasts | Data & Retrieval |
| run\_m2, run\_linear\_fallback | Feature file | water\_level\_forecasts | Forecasting |
| evaluate\_hazard, classify\_risk, scenario\_envelope | Features, config | assessments, assessment\_horizons | Flood Risk Analysis |
| attribute\_shapley, treeshap\_m2, find\_similar\_events, render\_narrative | Assessment, evidence | risk\_factors, explanations, evidence\_items | RCA & Explanation |
| apply\_policy, plan\_routes, rank\_shelters, match\_resources, draft\_alert | Assessment, policy, graph | recommendations, evacuation\_routes, alerts (DRAFT only), alert\_versions | Decision & Recommendation |

The worker's database identity can create alerts only in DRAFT (§9.8); the tool layer has no function that changes an alert to APPROVED or DISPATCHED.

### 21.4 Confidence propagation

Each agent reports a confidence cap in \[0, 1\]. The run's confidence is the minimum of the caps and the risk confidence C; no agent can raise it.

## 23. Orchestration with LangGraph

### 23.1 Two graphs

```
 analysis graph (worker; every cycle)
 START > plan > retrieve > qa_gate > forecast > risk > triage > explain > decide > policy_check > persist_drafts > END
                             |  missing data: fallback_data (retry once) > qa_gate
                             |  still missing: abstain > review_request > END
                         triage: no ward at MEDIUM or above > log_only > END

 dispatch graph (dispatcher service; one run per approved alert)
 START > load_approved > publish_routes > notify > schedule_outcome_capture > END
   (starts only from DB status APPROVED; a failure leaves the alert APPROVED and creates an operator task)
```

A human decision is a state change written by the oversight service; nothing waits in memory, so the system survives a restart between draft and approval.

### 23.2 Analysis graph rules

| Aspect | Rule |
| --- | --- |
| State | RunState (TypedDict): request, data package, forecasts, risk results, explanations, drafts, retried flag, trace |
| Routing | Plain Python functions over RunState; no LLM involvement |
| Concurrency | One RUNNING analysis per scenario or live environment, guarded by a PostgreSQL advisory lock; a second request returns 409 |
| Timeouts | Node 30 s (then FAILED), run 120 s |
| Retry | One retry per node; fallback\_data runs once |
| Degraded run | Allowed only if the lost output is not safety-critical; otherwise the run FAILED and an operator task is created |
| Idempotency | persist\_drafts skips a ward that already has an open alert at the same severity and appends the new assessment as evidence to it |
| Escalation | A higher severity arrives as a new assessment with its own alert; the older open alert for the ward becomes EXPIRED with reason SUPERSEDED |
| Trace | Each node appends name, start, end, status and input hash to agent\_runs.trace |

### 23.3 Triggers

| Trigger | Condition |
| --- | --- |
| SCHEDULE | Every 10 clock minutes; every 5 while any ward is MEDIUM or above |
| INGEST\_EVENT | A ward has r15 above 5 mm, or a sensor fill ratio above 0.5, or rise\_5 above 0.3 cm per minute; debounce 5 minutes per ward |
| MANUAL | POST /api/v1/assessments by an operator |
| SIMULATION | Each scenario step during a replay |

### 23.4 Dispatch graph rules

load\_approved re-reads the alert and refuses to proceed unless status is APPROVED and the approving review matches the current version. publish\_routes sets published = true on the approved routes. notify sends per recipient group, idempotent on (alert, version, channel, audience), with three retries and exponential backoff; the status change to DISPATCHED is made by the dispatcher database role after at least one delivery succeeds. schedule\_outcome\_capture registers the outcome job for the end of the horizon plus 30 minutes.

## 24. LLM Modes and Guardrails

### 24.1 Modes

| Mode | Behaviour | Default for |
| --- | --- | --- |
| off | No LLM call; template narrative only | Tests, CI, backup demo |
| template | Same as off, but explicitly the shipped production mode | Normal operation |
| llm | A local or remote model paraphrases the template output; output validated; discard on any failure | Optional demo |

Switch is LLM\_MODE in the environment. The system must pass its full test suite with LLM\_MODE=off (R7).

### 24.2 What the model receives and may do

The model receives only structured facts that already exist in the database (factor labels, contribution percentages, times, ward name, level, confidence class, evidence ids) and the instruction to rephrase them in at most 90 words. It has no tools, no database access and no ability to change anything. It must not add numbers, place names or advice, and must not express certainty beyond the supplied confidence class.

### 24.3 Validation

Same validator as §20.6: cited evidence ids exist for the run and ward; every number appears among the supplied facts at the displayed precision; no place name outside the facts; no sentence matching instruction patterns (evacuate, avoid, move, stay, do not); length limit. Any failure falls back to the template, logs the reason and marks narrative\_source TEMPLATE.

### 24.4 Prompt-injection defence

The model never sees free text from users, documents or the web, only generated structured facts. Its output is treated as untrusted text and validated before it is stored. Alert text for the public never comes from the model: only approved templates (§28.2) are used for instructions.

### 24.5 Deployment options

Ollama in the optional llm profile serving a 7 to 9 billion parameter model through an OpenAI-compatible adapter (a Narrator interface with TemplateNarrator and OpenAICompatibleNarrator implementations). A remote endpoint is allowed only if configured explicitly; no other component depends on it.

## 25. Human Oversight and the Approval State Machine

### 25.1 What needs a human

| Item | Approver role | Note |
| --- | --- | --- |
| MEDIUM advisory shown on the municipal dashboard | Municipal operator | Acknowledgement, no public message |
| HIGH or VERY\_HIGH public alert | Emergency coordinator | Checklist enforced by API and database |
| Any evacuation recommendation or resource-deployment request | Emergency coordinator | Part of the alert review |
| Promotion of a model or calibration to ACTIVE | Emergency coordinator or admin, with a recorded reason | §34 |
| Change to a policy file | Pull-request review by two people | Git history is the record |

Time is never consent: there is no auto-approval. A draft that is not reviewed expires (§25.9). An admin can manage users and keys but cannot approve a WARNING or URGENT alert (separation of duties).

### 25.2 State machine

```
 DRAFT --> PENDING_REVIEW --> APPROVED --> DISPATCHED --> OUTCOME_CAPTURED
   |            |                |             |
   |            +--> REJECTED    +--> EXPIRED  +--> EXPIRED (time to live elapsed)
   +--> ABSTAINED  (system declined to draft; reason recorded)
   (created directly) INSUFFICIENT_EVIDENCE  (assessment could not be made; shown to operators)
   +--> FAILED  (technical failure; operator task created)
   +--> EXPIRED (not reviewed in time)
```

| Transition | Actor | Precondition | Side effects |
| --- | --- | --- | --- |
| (new) to DRAFT | Decision agent through the worker identity | Assessment state ASSESSED with level MEDIUM or above | alert\_versions row 1 created by AGENT; audit |
| DRAFT to PENDING\_REVIEW | Worker | Draft passes contract validation and the policy check | Review queue entry; audit |
| DRAFT to ABSTAINED | Orchestrator | Explanation unavailable or evidence rule failed | Reason recorded; operator task |
| (new) to INSUFFICIENT\_EVIDENCE | Risk agent | Assessment state INSUFFICIENT\_EVIDENCE during an active event | Visible in the queue; cannot be approved or dispatched |
| PENDING\_REVIEW to APPROVED | Reviewer (role by severity) | Approving review for the current version; checklist complete | Review row, audit; dispatch graph may start |
| PENDING\_REVIEW to REJECTED | Reviewer | Reason code | Review row, audit; REANALYSIS\_REQUESTED starts a fresh run |
| APPROVED to DISPATCHED | Dispatcher role | Database guard re-checks the approving review for the current version | Deliveries created; audit |
| DISPATCHED to OUTCOME\_CAPTURED | Learning service | Outcome recorded for the assessment | Outcome row; audit |
| Any open state to EXPIRED | Worker or coordinator | TTL elapsed, superseded by a higher-severity alert, cancelled, or conditions cleared | terminal\_reason recorded |
| Any non-terminal state to FAILED | Worker or dispatcher | Technical failure after retries | Operator task; audit |

### 25.3 Reason codes

REJECTED: FALSE\_POSITIVE, INSUFFICIENT\_EVIDENCE, WRONG\_AREA, REANALYSIS\_REQUESTED, OTHER. EXPIRED: TTL\_ELAPSED, SUPERSEDED, CANCELLED, CONDITIONS\_CLEARED. ABSTAINED: EXPLANATION\_UNAVAILABLE, EVIDENCE\_RULE, POLICY\_BLOCK. FAILED: DISPATCH\_FAILED, ANALYSIS\_FAILED, ROUTING\_FAILED.

### 25.4 Review workflow

The reviewer opens a queue item showing the level, hazard interval, confidence class, data age, the ranked factors with evidence links, similar events, recommended actions, candidate routes and the exact alert text. Approval requires ticking evidence\_reviewed, risk\_reviewed and recommendations\_reviewed (enforced by the API and by a database CHECK); the API additionally requires uncertainty\_acknowledged when confidence is MEDIUM or LOW and simulated\_acknowledged when uses\_simulated\_inputs is true. A URGENT alert asks for a second confirmation in the UI.

### 25.5 Modifications

A reviewer may lower the severity, narrow the area, remove channels or audiences, shorten the expiry, or choose among approved template variants. A reviewer may not raise the severity or add free text. A modification inserts alert\_versions row n + 1 (created\_by REVIEWER), sets current\_version to n + 1, and the approval review refers to that version.

### 25.6 Stale approvals and concurrency

Approve and reject calls carry alert\_version. The service locks the alert row with SELECT ... FOR UPDATE, compares versions, and returns HTTP 409 if the version is stale. The database guard rejects an approval for a non-current version.

### 25.7 Roles and permissions

| Capability | Public | Operator | Coordinator | Admin | Researcher | System service | Dispatcher |
| --- | --- | --- | --- | --- | --- | --- | --- |
| View public map and active approved alerts | Yes | Yes | Yes | Yes | Yes | No | No |
| Ingest data (with device key) | No | No | No | No | No | Yes | No |
| Run analysis, draft alerts | No | Manual run only | Manual run | No | No | Yes | No |
| Approve or reject ADVISORY | No | Yes | Yes | No | No | No | No |
| Approve or reject WARNING or URGENT | No | No | Yes | No | No | No | No |
| Cancel an alert | No | No | Yes | Yes | No | No | No |
| Dispatch an APPROVED alert | No | No | No | No | No | No | Yes |
| Promote or roll back a model | No | No | Yes | Yes | No | No | No |
| Manage users and keys, edit config | No | No | No | Yes | No | No | No |

### 25.8 Audit

Every transition, review, promotion, key change and configuration change calls audit\_append (§9.8), which chains rows with a SHA-256 hash of the previous row. scripts/verify\_audit\_chain.py recomputes the chain and fails on any break; the System Health page shows the last verification.

### 25.9 Expiry and stand-down

A DRAFT or PENDING\_REVIEW alert expires after 30 minutes (configurable) with TTL\_ELAPSED. A DISPATCHED alert expires at expires\_at or on cancellation. When a ward stays below MEDIUM for two consecutive cycles, the system creates a PROPOSE\_STAND\_DOWN task for the coordinator; a public all-clear message is a future feature, not part of the MVP.

## 26. Decision and Recommendation Engine

### 26.1 Policy files

config/policy.prototype.yaml carries official: false and drives the MVP. config/policy.official.yaml exists and is empty until an authority supplies rules; if it is non-empty it takes precedence and the PROTOTYPE POLICY badge disappears. The footer of the UI always states which policy is active, with its hash.

### 26.2 Prototype rules

| Assessed level | Confidence condition | Actions (priority; approval) |
| --- | --- | --- |
| LOW | any | None; the ward is logged |
| MEDIUM | any | MONITOR (3; none), NOTIFY\_OPERATORS (2; operator) |
| HIGH | any | PREPARE\_ROUTES (2; none), PUBLIC\_WARNING (1; coordinator), OPEN\_SHELTERS (2; coordinator); TRAFFIC\_DIVERSION (2; coordinator) if a subway lies in the footprint; MEDICAL\_STANDBY (2; coordinator) if a hospital lies in the footprint |
| VERY\_HIGH | C at least 0.40 | All HIGH actions plus EVACUATION\_RECOMMENDATION (1; coordinator), DEPLOY\_RESCUE (2; coordinator), DEPLOY\_PUMPS (2; coordinator) |
| VERY\_HIGH | C below 0.40 | All HIGH actions plus REQUEST\_HUMAN\_ASSESSMENT (1; coordinator); no evacuation or deployment drafted |
| HIGH or above | Substitute inputs or SENSOR\_LOSS\_HOLD | Adds REQUEST\_HUMAN\_ASSESSMENT |
| INSUFFICIENT\_EVIDENCE | not applicable | REQUEST\_MORE\_DATA (1; operator) |

Rule conflicts resolve to the lowest priority number. requires\_approval on the alert is true if any action needs approval, which is every case from HIGH upward.

### 26.3 Resource matching

Resource demand uses placeholder ratios in config/response.prototype.yaml, labelled PLACEHOLDER (for example one pump team per eligible ward footprint above a stated population). Matching is greedy: the nearest available simulated resource by routed travel time. Every resource row is simulated; the output is a proposal, never a dispatch.

### 26.4 Shelter ranking

Only official shelters with status OPEN or UNKNOWN within 8 km of the footprint are candidates. Capacity is shown as 'unknown' when null and is never a ranking term (R11). Ranking uses the safe-route score (§27.5).

### 26.5 Tests

Table-driven tests for each row of §26.2; a test that a LOW-confidence VERY\_HIGH never contains EVACUATION\_RECOMMENDATION or deployment actions; a test that a draft with a subway in the footprint contains TRAFFIC\_DIVERSION; a test that official policy overrides prototype policy when present.

## 27. Evacuation Routing and Shelter Selection

### 27.1 Graph

OSMnx builds a drive graph for the GCC boundary plus a 2 km buffer and keeps the largest strongly connected component. Edge attributes: length\_m, speed\_kph, travel\_time\_s, is\_underpass (a GCC vehicular subway within 15 m, or an OSM tunnel or negative layer), is\_bridge. graph\_version is the first 12 hex characters of the SHA-256 of the sorted edge list and is stored with every route. The graph is rebuilt monthly by scripts/build\_graph.py.

### 27.2 Edge risk

Edge risk r\_e is the highest ward risk value among the footprint cells that the edge crosses, using LOW 0, MEDIUM 0.4, HIGH 0.7 and VERY\_HIGH 1.0, applied only to footprint cells. An underpass takes at least 0.6 when its ward is MEDIUM or above and is blocked at HIGH or above. A sensor at overflow within 50 m sets r\_e to 1.

### 27.3 Cost and search

Cost = travel\_time\_s x (1 + 4 x r\_e); an edge with r\_e of 0.9 or more is removed (the weight function returns None). Origin: the footprint centroid snapped to the nearest graph node. Candidates: official shelters within 8 km. Dijkstra gives the five cheapest candidates; an alternative path to each uses a 1.5 times penalty on the edges of the first path; the best three routes after scoring are returned.

### 27.4 Output

For each route: geometry, length, ETA, maximum edge risk, number of blocked edges avoided, warnings (for example 'passes within 100 m of a flooded subway'), the shelter, and the graph version. Candidate routes are stored with published = false.

### 27.5 Safe-route score

SRS = 1 - (0.35 tau + 0.45 rho + 0.20 kappa), where tau = min(1, ETA / 30 min), rho = 0.5 x the length-weighted mean of r\_e + 0.5 x the maximum r\_e, and kappa = max(shelter site risk, status penalty) with the penalty 0 for OPEN, 0.3 for UNKNOWN and 1 for FULL. Capacity is not a term. The weights are ASSUMED.

### 27.6 No route and degraded mode

If no unblocked route exists, the output is 'no safe route found' and a REQUEST\_HUMAN\_ASSESSMENT task. If the graph is missing or routing fails, the system lists the nearest official shelters by straight-line distance, marks them approximate, and creates an operator task.

### 27.7 Publication and limits

The review panel shows candidate routes. publish\_routes in the dispatch graph sets published = true after the alert is APPROVED; the public map shows only published routes of active alerts. Limits: driving only; no live traffic; no live road-closure feed; shelter locations are geocoded from a PDF list.

## 28. Alert Generation and Delivery

### 28.1 Content

An alert version holds the severity, headline, description, instruction (from templates), ward and footprint geometry, onset (time to impact, interpolated), expiry, confidence class, routes, shelters, recommended actions, and the labels SIMULATED and PROTOTYPE when they apply. The public text never contains a number that is not in the structured content.

### 28.2 Templates

Text comes from config/alert\_templates/en.yaml and ta.yaml with named variables (ward name, level, onset, expiry, shelter names). Templates are authored and reviewed by a Tamil speaker and by an authority before official use; the MVP ships clearly marked demonstration wording. Nothing is machine-translated at runtime, and a language model never writes instruction text.

### 28.3 Channels

### 28.4 CAP alignment

The alert payload follows the Common Alerting Protocol field set and is always status Exercise in the prototype. ADVISORY maps to severity Minor, urgency Future, certainty Possible; WARNING to Moderate, Expected, Likely; URGENT to Severe, Immediate, Likely. The identifier combines the alert id and version; the area carries the ward polygon; parameters carry the assessment id, the confidence class and uses\_simulated\_inputs.

### 28.5 Dispatch rules

Recipients are audience groups per ward, not individuals; the MVP stores no citizen personal data. Delivery is idempotent on (alert, version, channel, audience) with three retries. At most one new alert per ward is created every 30 minutes unless the severity rises. A real SMS or voice integration would need legal review under India's Digital Personal Data Protection Act 2023 and telecom sender rules before any phone number is stored.

### 28.6 Failure

A failed delivery leaves its row FAILED, creates an operator task, and does not hide the alert from the dashboards. The alert moves to DISPATCHED when at least one delivery succeeded; if none did, it stays APPROVED and an operator can retry.

### 28.7 Tests

One delivery per (alert, version, channel, audience); simulated channels never report real delivery; the Mailpit message carries the SIMULATED label when inputs were simulated; a modified alert is delivered with the modified text only.

Environment variables override YAML. YAML files are validated at start-up by Pydantic models; an invalid file stops the service with a clear message. config\_hash = the first 16 hex characters of SHA-256 over the canonical JSON of the effective configuration without secrets; it is stored in config\_versions and with every run, assessment and audit entry that depends on it.

## 33. MLOps and Model Registry

### 33.1 Lifecycle

Data manifest, training script (train\_m1.py or train\_m2.py), evaluation (evaluate.py writes reports/eval\_\<date>.json), CANDIDATE row in model\_versions, shadow evaluation, human promotion to ACTIVE, optional rollback. Nothing skips a step.

### 33.2 Registry rules

| Rule | Mechanism |
| --- | --- |
| One ACTIVE model per name | Partial unique index (§9.3) |
| Artifact integrity | SHA-256 verified on every load; a mismatch triggers the fallback model and an alert on the health page |
| Traceability | git sha, dataset manifest hash, parameters, metrics, trained\_on\_simulated and labels stored with the row |
| Promotion gates | M1: spatial-CV targets of §14.7 reported and reviewed. M2: gates of §15.5 per horizon. Calibration: shadow Brier and CSI no worse than ACTIVE by more than 5 percent relative |
| Human promotion | Coordinator or admin with a reason; audit entry |

### 33.3 Reproducibility

Seeds live in config; LightGBM runs with deterministic mode, row-wise histogram construction and one thread when reproducing; uv.lock and pinned image tags fix the environment; `make repro` retrains M1 and M2 from the manifest and compares metrics with the stored values within a stated tolerance. runs/experiments.jsonl logs every training run.

### 33.4 Model cards

Each registry row carries a card: intended use, training data and manifest hash, features, metrics with their labels (SYNTHETIC-VALIDATION where applicable), known limitations, and the date. The UI shows the card next to every model-derived number.

### 33.5 Rollback

`python -m aquarizz.learning.promotion rollback <name>` or POST /models/{name}/rollback retires the current ACTIVE row and restores the previous one in a single transaction and writes an audit entry.

### 33.6 Drift

The learning service computes the population stability index for r60, fill\_ratio and S\_w against the training distribution. A value above 0.2 raises a recommendation to run a learning evaluation. Drift never retrains a model by itself.

## 34. Controlled Learning and Outcome Feedback

### 34.1 Outcome sources

| Source | Use | Label |
| --- | --- | --- |
| HISTORICAL\_LAYER | Hindcast against real historical flood points and polygons | OBSERVED labels, sparse |
| SIM\_GROUND\_TRUTH | Simulated overflow per ward | SYNTHETIC-VALIDATION |
| OPERATOR\_REPORT | Reports entered by operators | OBSERVED (once real operations exist) |
| SATELLITE | Sentinel-1 extents | STRETCH |
| CITIZEN\_REPORT | Not built | Not applicable |

### 34.2 Pairing

A prediction (ward, as\_of, horizon) is paired with an outcome observed in (as\_of, as\_of + horizon + 30 minutes\]. A prediction counts as positive when H is at least 0.60 at that horizon (configurable). Pairs inherit the label of their outcome source.

### 34.3 Metrics

Probability of detection, false-alarm ratio and critical success index; precision, recall and F1; Brier score; a five-bin reliability table and the expected calibration error; lead time (observed first impact minus the first time H reached 0.60); footprint IoU, precision and recall at cell level where an observed extent exists. Intervals come from bootstrap resampling of events (1,000 resamples). With fewer than five independent events the report says 'insufficient events' and makes no claim.

### 34.4 Error analysis

Mean Shapley contributions for false alarms versus hits; sensor coverage; S\_w versus outcome; confidence class; the ten worst wards. The output is a text list of proposals for people to read; it changes nothing.

### 34.5 What learning may and may not change

| May propose | May not change |
| --- | --- |
| Calibration parameters b and T (§16.7) | Policy matrix, floors, hold rules |
| Alert threshold H = 0.60 by minimising cost (miss to false alarm ratio 5 to 1, ASSUMED; needs 30 pairs and 3 positives) | Approval rules, roles, audit |
| Ramp bounds and priors, by leave-one-event-out Brier (needs 3 events) | Risk-level cut points |
| Retrained M1 or M2 on new labels or telemetry | Anything in production without human promotion |

### 34.6 Triggers

At least 30 new paired outcomes; Brier score at least 10 percent worse (relative) than at promotion over the last 50 pairs; PSI above 0.2 on r60, fill\_ratio or S\_w; or a manual request. Triggers start an evaluation, not a promotion.

### 34.7 Promotion gate

Shadow evaluation of the candidate against ACTIVE on the same recent window: Brier and CSI no worse than 5 percent relative; all tests pass; a coordinator or admin approves with a reason; the audit log records it.

### 34.8 Demonstration protocol

Recalibrate on outcomes that exclude the replayed event, then apply the candidate to the replayed event, so the comparison is out of sample. Show Brier, ECE and the reliability table before and after, each labelled with its source (SYNTHETIC-VALIDATION for simulated outcomes, HINDCAST for historical ones). The result may show no improvement, and it is shown as it is.

### 34.9 Not claimed

Online learning; automatic promotion; any accuracy, IoU or lead-time figure that the evaluation harness did not produce.

## 35. Failure Handling and Degraded Modes

| Failure | Detection | Behaviour | Visible effect |
| --- | --- | --- | --- |
| No rainfall data | Source age above 60 min | Refresh once; use cache up to 6 h flagged STALE; then no rainfall-driven hazard | Wards with sensors continue at lower confidence; others INSUFFICIENT\_EVIDENCE with the reason |
| Forecast empty or older than 3 h | Source age | Persistence only; beyond 15 min the horizons use observations only | Forecast chip shows STALE |
| Sensor offline | No reading for three intervals | Excluded from features; neighbour sensors within 1.5 km considered | n\_valid falls; confidence falls |
| All sensors in a ward lost | n\_valid 0 | Substitution mode (§16.4); hold rule if the previous level was HIGH or above | uses\_substitute\_inputs; REQUEST\_HUMAN\_ASSESSMENT |
| Stuck or spiking sensor | QC flags | Reading quality 0, excluded | Flag shown |
| M2 missing or hash mismatch | SHA check at load | Linear fallback; health page error | method LINEAR\_FALLBACK |
| M1 missing | Load failure | Fixed-weight fallback index | FALLBACK\_MODEL label |
| Database unavailable | Connection errors | Writes return 503; dashboards serve a snapshot up to 60 s old; worker pauses with backoff; no dispatch; approvals disabled | Banner on every page |
| LLM unavailable or invalid output | Timeout or validation failure | Template narrative | narrative\_source TEMPLATE |
| Routing unavailable | Exception or missing graph | Straight-line nearest official shelters marked approximate | Operator task |
| Invalid geometry | ST\_IsValid | ST\_MakeValid, quarantine; build fails if area changes by more than 5 percent | Build log |
| Worker stalled | Heartbeat older than three cadence intervals | Restart policy unless-stopped; health page error | System health red |
| Notification failure | Delivery status | Three retries; operator task | FAILED row |
| Clock skew | Timestamp more than 2 min ahead | CLOCK\_SKEW flag; ordering by receive time | Flag shown |
| Analysis exception for one ward | Exception in the engine | That ward FAILED, others continue | Ward hatched with reason |
| Analysis run over 120 s | Run timeout | Run FAILED; operator task | System health |
| Stale approval | Version mismatch | 409; reviewer reloads the current version | Message |
| Dispatch before approval | Trigger | Exception raised by the database | Never reaches the public |

A degraded run is allowed only when the lost output is not safety-critical; otherwise it fails visibly and creates an operator task.

## 36. Security, Privacy and Governance

### 36.1 Threats and controls

| Threat | Control |
| --- | --- |
| Forged sensor data | Per-device keys; QC flags; neighbour checks; simulated sensors clearly marked |
| Replay of old readings | Timestamp window; UNIQUE (sensor, time) |
| False alert injection | Human gate; database dispatch guard; dispatcher role separation |
| Prompt injection | The model sees only generated structured facts, has no tools, and its output is validated |
| Privilege escalation | RBAC in routers and database roles; admin cannot approve WARNING or URGENT |
| Audit tampering | Append-only triggers; hash chain; verification script |
| Ingestion flooding | Body limit 1 MB; batch limit 1,000; rate limits |
| Vulnerable dependencies | Lockfiles; pip-audit and npm audit in CI; pinned images |

### 36.2 Hardening

TLS at the reverse proxy for any shared deployment; CORS allow-list from the environment; bound parameters only; no stack traces in responses; request\_id in every log line; non-root containers; secrets only in .env.

### 36.3 Privacy

The MVP stores no citizen personal data. Alert recipients are audience groups per ward. Operator email addresses live only in users. Logs avoid personal data. If real phone numbers are ever used, legal review under the Digital Personal Data Protection Act 2023 comes first.

### 36.4 Governance

Prototype thresholds are labelled and owned by the project team until an authority supplies official rules. Model cards state limitations. Known biases are documented: population layers are modelled, OpenStreetMap coverage varies by neighbourhood, flood labels are sparse and skew towards well-reported areas. Accountability for every public alert rests with the approving person, recorded in the audit log.

### 36.5 Not covered

Penetration testing; asymmetric JWT signing; multi-node hardening.

## 39. Evaluation Methodology and Acceptance Criteria

### 39.1 Principles

Baselines appear in every table. Events, not rows, are the unit of independence. Confidence intervals come from bootstrapping events. Every metric carries its label. Targets below are proposals to be measured; they are not results. No claim leaves the project without a run id from the harness.

### 39.2 Targets

| Component | Data | Metrics | Baselines | Target | Label |
| --- | --- | --- | --- | --- | --- |
| M1 | Real labels, spatial CV | ROC-AUC, PR-AUC, Brier, Continuous Boyce Index, hazard-zone overlap | Logistic regression, fixed-weight index | AUC at least 0.70; CBI at least 0.5; overlap at least twice chance | Spatial CV on incomplete labels |
| M2 per horizon | Simulated storms, domain-shift set | RMSE, skill score, pinball loss, coverage, lead time | Persistence, linear extrapolation | Skill above 0 against both; coverage 0.70 to 0.90 | SYNTHETIC-VALIDATION |
| M3 | Outcome pairs | Brier, ECE, reliability | Uncalibrated priors | ECE at most 0.10 on held-out pairs; Brier better than uncalibrated | By calibration source |
| End to end | At least 100 simulated storms | POD, FAR, CSI, median lead time to first impact | Rainfall-threshold-only classifier; plain weighted sum | POD at least 0.70; FAR at most 0.50; median lead time at least 30 min | SYNTHETIC-VALIDATION |
| Policy ablation | Same storms | False alerts on dry or low-hazard high-exposure wards | Plain weighted sum | Zero alerts from exposure alone | SYNTHETIC-VALIDATION |
| System | Load test | Cycle time, alert latency, freshness | None | Targets of §37.3 | MEASURED |

### 39.3 Scenario batch protocol

The simulator generates at least 100 storms varying peak intensity, duration, shape, spatial factor and sensor parameters; the gated engine runs on each against the simulated ground truth; the harness reports POD, FAR, CSI and lead time with event-bootstrap intervals and shows the distribution, not only the mean. All figures are SYNTHETIC-VALIDATION.

### 39.4 Baselines

### 42.1 Risk engine (src/aquarizz/risk/engine.py, pure functions)

```python
from __future__ import annotations
import math
from dataclasses import dataclass

LEVELS = ['LOW', 'MEDIUM', 'HIGH', 'VERY_HIGH']
PERMITTED = {0: (0, 0), 1: (0, 1), 2: (1, 2), 3: (2, 3)}      # band -> (lowest, highest) level index

def ramp(x: float, lo: float, hi: float) -> float:
    return min(1.0, max(0.0, (x - lo) / (hi - lo)))

def sigmoid(z: float) -> float:
    return 1.0 / (1.0 + math.exp(-z))

@dataclass(frozen=True)
class Inputs:
    rain_hr_eq: float
    r180: float
    a72: float
    s_w: float
    fill_ratio: float | None = None       # None together with rise None means substitution mode
    rise: float | None = None             # cm per minute
    drain_stress_rho: float | None = None

def hazard(inp: Inputs, cfg: dict, b: float = 0.0, t: float = 1.0):
    w, rp = cfg['weights'], cfg['ramps']
    f = {
        'rain_intensity': ramp(inp.rain_hr_eq, *rp['rain_hr_eq']),
        'rain_accumulation': ramp(inp.r180, *rp['r180']),
        'antecedent': ramp(inp.a72, *rp['a72']),
        'susceptibility': inp.s_w,
    }
    if inp.fill_ratio is not None and inp.rise is not None:
        f['water_level'] = ramp(min(inp.fill_ratio, 1.2), *rp['fill_ratio'])
        f['level_rise'] = ramp(max(inp.rise, 0.0), *rp['rise_cm_min'])
    else:
        f['drain_stress_model'] = ramp(inp.drain_stress_rho, *rp['drain_stress_rho'])
    z = cfg['intercept'] + sum(w[k] * v for k, v in f.items())
    return sigmoid((z - b) / t), z, f

def band(h: float, cuts=(0.10, 0.40, 0.70)) -> int:
    return sum(h >= c for c in cuts)

def level_index(h: float, impact: float, cuts=(0.10, 0.40, 0.70), theta: float = 0.5) -> int:
    lo, hi = PERMITTED[band(h, cuts)]
    return hi if (hi > lo and impact >= theta) else lo

def impact(e: float, v: float, we: float = 0.6, wv: float = 0.4) -> float:
    return we * e + wv * v

def floor_index(sensors: list[dict], rain_hr_eq_now: float, cfg: dict):
    # sensors: valid readings only (quality > 0, not stale): {fill_ratio, rise}
    best, why = 0, None
    for s in sensors:
        if s['fill_ratio'] >= cfg['f1_fill'] and best < 2:
            best, why = 2, 'F1'
        elif s['fill_ratio'] >= cfg['f2_fill'] and s['rise'] >= cfg['f2_rise'] and best < 1:
            best, why = 1, 'F2'
    if rain_hr_eq_now >= cfg['f3_rain'] and best < 1:
        best, why = 1, 'F3'
    return best, why

def assess(h_by_horizon: dict[int, float], imp: float, floor_idx: int, cfg: dict):
    cuts, theta = cfg['cuts'], cfg['impact_threshold']
    per = {h: level_index(p, imp, cuts, theta) for h, p in h_by_horizon.items()}
    actionable = max(per[h] for h in (0, 15, 30, 60) if h in per)
    level = max(actionable, floor_idx)
    watch = 120 in h_by_horizon and band(h_by_horizon[120], cuts) >= 2 and level < 2
    return level, per, watch

def time_to_impact(h_by_horizon: dict[int, float], onset: float = 0.60):
    pts = sorted(h_by_horizon.items())
    if pts[0][1] >= onset:
        return 0.0
    for (t1, a), (t2, c) in zip(pts, pts[1:]):
        if c >= onset:
            return t1 + (onset - a) / (c - a) * (t2 - t1)
    return None

def confidence(q_cov: float, q_fresh: float, q_valid: float, h_low: float, h_high: float, a_ev: float):
    q = min(q_cov, q_fresh, q_valid)
    return q * (1.0 - min(1.0, h_high - h_low)) * a_ev, q

def hold_and_hysteresis(new_idx: int, prev_idx: int, data_ok: bool, minutes_since_prev: float,
                        cycles_below: int, minutes_below: float):
    if not data_ok and prev_idx >= 2 and minutes_since_prev < 30:
        return prev_idx, 'SENSOR_LOSS_HOLD'
    if new_idx >= prev_idx:
        return new_idx, None
    if cycles_below >= 2 and minutes_below >= 20:
        return prev_idx - 1, None
    return prev_idx, None
```

### 42.2 Exact Shapley (src/aquarizz/explain/shapley.py)

```python
from itertools import combinations
from math import factorial

def exact_shapley(value_fn, actual: dict, base: dict) -> dict:
    players = list(actual)
    n = len(players)
    if n > 12:
        raise ValueError('above 12 players use permutation sampling and label it APPROXIMATE')
    cache: dict = {}
    def v(coalition: frozenset) -> float:
        if coalition not in cache:
            cache[coalition] = value_fn({p: (actual[p] if p in coalition else base[p]) for p in players})
        return cache[coalition]
    phi = {}
    for p in players:
        rest = [q for q in players if q != p]
        total = 0.0
        for k in range(n):
            weight = factorial(k) * factorial(n - k - 1) / factorial(n)
            for c in combinations(rest, k):
                s = frozenset(c)
                total += weight * (v(s | {p}) - v(s))
        phi[p] = total
    return phi

def contributions(phi: dict) -> list[dict]:
    pos = {k: max(x, 0.0) for k, x in phi.items()}
    total = sum(pos.values()) or 1.0
    rows = [{'factor_key': k, 'shapley_value': x, 'contribution_pct': 100.0 * pos[k] / total,
             'direction': 'INCREASES' if x >= 0 else 'DECREASES', 'method': 'EXACT_SHAPLEY'} for k, x in phi.items()]
    rows.sort(key=lambda r: -r['shapley_value'])
    for i, r in enumerate(rows, 1):
        r['rank'] = i
    return rows
```

The value function for a ward is v(x) = sigmoid(z(x)) times (0.5 + 0.5 x impact(E, V)), with the baseline of §20.2; the efficiency test asserts that the values sum to v(actual) minus v(baseline).

### 42.3 Hydrology and sensor simulator (src/aquarizz/hydrology/scs.py)

```python
import math

def scs_runoff(p_cum_mm: float, cn: float, lam: float = 0.2) -> float:
    s = 25400.0 / cn - 254.0
    ia = lam * s
    return 0.0 if p_cum_mm <= ia else (p_cum_mm - ia) ** 2 / (p_cum_mm - ia + s)

def manning_capacity(width_m, depth_m, invert_start_m, invert_end_m, length_m, covered=False, n=0.015):
    if min(width_m, depth_m, length_m) <= 0 or None in (invert_start_m, invert_end_m):
        return None                                         # leaves attrs_complete false
    slope = max((invert_start_m - invert_end_m) / length_m, 0.0005)
    area = width_m * depth_m
    perimeter = 2 * (width_m + depth_m) if covered else width_m + 2 * depth_m
    return (1.0 / n) * area * (area / perimeter) ** (2.0 / 3.0) * math.sqrt(slope)

class SensorSim:
    def __init__(self, built, depth_cm, kappa, lag_min, k, blockage, tide_amp=0.0, noise_cm=0.5, rng=None):
        self.cn = 60.0 + 38.0 * built
        self.depth, self.kappa, self.k, self.b, self.tide_amp = depth_cm, kappa, k, blockage, tide_amp
        self.noise, self.rng = noise_cm, rng
        self.p_cum = self.h = self.pond = 0.0
        self.queue = [0.0] * (lag_min + 1)
        self.flooded = False

    def step(self, minute: int, rain_mm_min: float) -> float:
        before = scs_runoff(self.p_cum, self.cn)
        self.p_cum += rain_mm_min
        self.queue.append(scs_runoff(self.p_cum, self.cn) - before)
        inflow = self.kappa * self.queue.pop(0)
        tide = 1.0 - self.tide_amp * max(0.0, math.sin(2 * math.pi * minute / (12.42 * 60)))
        self.h = max(0.0, self.h + inflow - self.k * self.h * (1.0 - self.b) * tide)
        if self.h > self.depth:
            self.pond += self.h - self.depth
            self.h = self.depth
            self.flooded = True
        self.pond *= 0.98
        return self.h + self.pond + (self.rng.normal(0.0, self.noise) if self.rng is not None else 0.0)
```

### 42.8 Risk-penalised routing (src/aquarizz/routing/plan.py)

```python
import networkx as nx

def make_weight(edge_risk: dict, block_at: float = 0.9, k: float = 4.0, extra: dict | None = None):
    extra = extra or {}
    def w(u, v, d):                                  # G is a simple DiGraph (best parallel edge kept at build time)
        r = edge_risk.get((u, v), 0.0)
        if r >= block_at or d.get('blocked'):
            return None
        return d['travel_time_s'] * (1.0 + k * r) * extra.get((u, v), 1.0)
    return w

def plan_routes(G, origin, shelters: dict, edge_risk: dict, n_routes: int = 3):
    base = make_weight(edge_risk)
    dist, paths = nx.single_source_dijkstra(G, origin, weight=base)
    reachable = sorted((dist[node], sid) for sid, node in shelters.items() if node in dist)[:5]
    options = []
    for cost, sid in reachable:
        options.append((sid, paths[shelters[sid]]))
        used = {(a, b): 1.5 for a, b in zip(paths[shelters[sid]], paths[shelters[sid]][1:])}
        try:
            alt = nx.shortest_path(G, origin, shelters[sid], weight=make_weight(edge_risk, extra=used))
            if alt != paths[shelters[sid]]:
                options.append((sid, alt))
        except nx.NetworkXNoPath:
            pass
    return rank_by_safe_route_score(G, options, edge_risk)[:n_routes]    # SRS of section 27.5
```

```python
from scipy.spatial import cKDTree
from sklearn.model_selection import GroupKFold

def block_id(x, y, size=5000.0):
    return np.floor(x / size).astype(int) * 100000 + np.floor(y / size).astype(int)

def m1_spatial_cv(X, y, xy, params, buffer_m=500.0, n_splits=5):
    groups, scores = block_id(xy[:, 0], xy[:, 1]), []
    for tr, te in GroupKFold(n_splits=n_splits).split(X, y, groups):
        near = cKDTree(xy[te]).query(xy[tr], k=1)[0] < buffer_m          # drop training cells next to the test block
        tr = tr[~near]
        model = lgb.LGBMClassifier(**params).fit(X[tr], y[tr])
        scores.append(evaluate_ranking(y[te], model.predict_proba(X[te])[:, 1]))
    return scores

                 colsample_bytree=0.8, random_state=42, deterministic=True, force_row_wise=True, n_jobs=1, verbose=-1)

def train_m2_horizon(X_tr, d_tr, X_va, d_va):
```

```python
    if len(text.split()) > 90:

    return errors                                            # empty list means accepted; otherwise use the template
```

## 43. Chennai End-to-End Demo Scenario

### 43.1 Scenario definition

The primary scenario is DEMO-STORM-01, a synthetic cloudburst over a Chennai ward cluster. A second, optional scenario replays a historical rainfall window from the Open-Meteo archive (the December 2015 event), bias-corrected to IMD daily totals; it is labelled REPLAY, and the narration says that reanalysis smooths local extremes. Both run on simulated sensors posting through the production endpoints, at 120 times real speed, seed 42.

DEMO-STORM-01 hyetograph (minutes from T0 to rain intensity in mm per hour, linear between knots): -180 to 0; -12 to 4; -6 to 20; 0 to 55; +4 to 92; +14 to 90; +30 to 75; +45 to 50; +60 to 20; +80 to 5; +120 to 2; +240 to 0. Rainfall from T-12 to T+60 is 71.6 mm and to T+120 is 77.9 mm. Antecedent 72-hour rainfall is set to 18 mm (ASSUMED).

| Ward | Role | Built fraction | Drain depth | kappa | lag | k | Static values used in the worked example |
| --- | --- | --- | --- | --- | --- | --- | --- |
| Hero ward | Storm hits a susceptible, exposed ward | 0.80 | 100 cm | 3.4 | 8 min | 0.02 | S\_w 0.78, E 0.82, V 0.64, I 0.75 (ILLUSTRATIVE) |
| Contrast ward | Same rain, better drained, less exposed | 0.45 | 120 cm | 1.2 | 12 min | 0.03 | S\_w 0.35, E 0.45, V 0.30, I 0.39 (ILLUSTRATIVE) |

The hero parameters are tuned so the scripted storm produces the timeline below; they are not calibrated to any real drain. The static values are illustrative placeholders for the worked example; the build computes the real ones.

### 43.2 Choosing the demo area by rule

scripts/select\_demo\_area.py selects a contiguous cluster of 8 to 15 wards that satisfies all of: (a) at least 80 percent of drain features have parseable width and depth; (b) every ward centroid lies within 3 km of a candidate shelter; (c) the cluster overlaps a historical flood layer; (d) at least 100,000 residents; (e) its road graph is connected. Starting candidates are the Velachery to Pallikaranai to Adyar corridor and Ambattur with Anna Nagar West. The hero ward is the cluster ward with the highest S\_w among those with impact at least 0.5 and at least three sensors; the contrast ward is a neighbour with S\_w below 0.4 and impact below 0.5. A ward is never chosen by name or because a diagram used it.

## 45. Troubleshooting

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Spatial join returns nothing | Mixed SRIDs | Check ST\_SRID on both sides; transform at the boundary only |
| ArcGIS paging repeats or skips features | No stable ordering | Order by object id and stop when a page returns fewer than 2,000 |
| GeoJSON coordinates look like metres | Projected CRS requested | Request 4326 and reproject locally |
| KML will not open | GDAL KML driver missing | Install the driver or convert with ogr2ogr in a container |
| DEM download fails | Bucket or tile path changed | Rerun the probe; fall back to SRTM then GLO-90 |
| Flow accumulation looks striped | Flats not resolved | Run resolve\_flats before flow direction |
| Open-Meteo returns 429 | Too many calls | One batched request per hour; respect the daily limit |
| Timestamps off by 5.5 hours | Naive timestamps treated as UTC | Require an offset; store UTC; display Asia/Kolkata |
| Every replayed reading is LATE | Validators use the wall clock | Use the clock service |
| Upsert reports no change | Same value posted again | Expected: DUPLICATE\_IGNORED |
| Dispatch raises a guard error | No approving review for the current version | Approve the current version; do not bypass the guard |
| LangGraph recursion limit | fallback\_data loops | It must set retried = true; test route\_after\_qa |
| Sensors never rise in the simulator | Unit mix of mm per hour and mm per minute | Convert once at the scenario boundary |
| Risk stays LOW during a storm | Stale rainfall, S missing, or sensors flagged | Check data age, S\_w and QC flags on the ward page |
| Map is blank | Basemap style unreachable | Use the blank-background fallback or set VITE\_BASEMAP\_STYLE\_URL |
| Browser blocks API calls | CORS allow-list | Add the origin to the allow-list |
| Model refuses to load | SHA-256 mismatch | Re-register the artifact or roll back; fallback runs meanwhile |
| Containers killed | Out of memory | Turn off the llm profile; close other applications |
| Tamil text shows boxes | Font missing | Bundle a Tamil-capable font in the web build |

## 46. What Not to Build

| Item | Why not in the MVP | When to reconsider |
| --- | --- | --- |
| Kafka, MQTT broker | About 69 thousand sensor rows per simulated day fit HTTP and PostgreSQL | Real telemetry above a few hundred devices |
| Redis, TimescaleDB, MinIO, vector database | No caching, partitioning or embedding need yet | Measured bottleneck |
| Kubernetes, microservices | One machine, one team, one demo | A multi-team production deployment |
| GRU or LSTM forecaster in the pipeline | No real telemetry to train or validate it | The gate in §15.7 |
| Radar nowcasting, ConvLSTM | No radar archive access verified | Access to IMD radar data |
| 2D hydrodynamic modelling (SWMM, HEC-RAS) | Needs surveyed drainage and calibration data | A partnership with GCC |
| Autonomous dispatch or auto-approval | Violates P1 and R1 | Never without legal and operational authority |
| Online learning, automatic model promotion | Violates ADR-013 | Governance and monitoring in place |
| Real SMS, IVRS or push | Needs consent, sender registration and legal review | An agreement with an operator |
| Language-model-written alert text or machine-translated Tamil at runtime | Safety wording must be reviewed by people | Never for instructions |
| Custom authentication server | JWT is enough for the prototype | OIDC single sign-on in production |
| Mobile apps | The responsive web app covers the demo | Field-team requirements |
| Real-time traffic routing | No live traffic licence | A traffic data agreement |
| 3D digital twin | Cost without decision value | Later visualisation work |
| Blockchain audit | The hash chain is enough | Never needed |

## 47. Known Limitations and Honest-Claims Register

### 47.1 Limitations

| ID | Limitation | Effect | Mitigation and what the product says |
| --- | --- | --- | --- |
| L1 | No live drain telemetry exists; sensors are simulated | Sensor-driven results are SIMULATED | Badge everywhere; same contract for real devices |
| L2 | M2 is trained and tested on simulated storms | Skill is SYNTHETIC-VALIDATION | Label printed with every metric; promotion gates; fallback |
| L3 | The DEM is a surface model with metre-scale vertical error | M1 ranks, it does not measure depth | Rank-scaled S; percentile features; noise-sensitivity test |
| L4 | Rainfall is reanalysis or NWP, not radar or gauges | Short convective bursts are smoothed | No 15-minute nowcast skill is claimed; scenario envelope |
| L5 | Flood labels are sparse and skewed to well-reported areas | M1 evaluated on incomplete labels | Presence-only caveat; Boyce index; never called validated |
| L6 | The drain capacity index is a proxy from partial attributes | Ranks wards only | Completeness shown; not a design calculation |
| L7 | The footprint is a set of 250 m cells | Not an inundation depth map | Described as an indicative flood-prone area |
| L8 | All thresholds and weights are prototype values | Not official | PROTOTYPE POLICY badge; policy.official empty |
| L9 | Delivery is simulated except sandbox email | No real public reach | Labelled SIMULATED in UI and messages |
| L10 | Shelter capacity is unknown and shelter locations are geocoded from a PDF | Routes end at candidate shelters | Capacity shown as unknown; geocode quality flagged |
| L11 | Population is a static modelled layer | Exposure ignores time of day | Stated in the explanation |
| L12 | Open-Meteo free tier is for non-commercial use | Cannot be used in a commercial product | Licence note in the registry; production path in §40 |
| L13 | Single-machine deployment | No high availability | Production path in §40 |
| L14 | The hazard index is not a probability until calibrated | Users may over-read it | Index wording; calibration status chip |
| L15 | Impact ranks are relative to the study area | E and V change if the set of wards changes | Documented; rebuilt with the data |
| L16 | Linear-fallback forecasts overshoot on rising limbs | Fallback may be pessimistic | method LINEAR\_FALLBACK shown; clipped to depth plus 100 cm |

## FINAL IMPLEMENTATION CONTRACT

This contract binds everyone who builds, extends or demonstrates AquaRizz. It restates the non-negotiable decisions of this guidebook in one place. Where any slide, earlier guide or conversation disagrees with this guidebook, this guidebook wins; to change it, record an ADR and obtain two reviews.

1. **Architecture.** AquaRizz is a modular monolith. Orchestration is two LangGraph graphs (analysis and dispatch). The only datastore is PostgreSQL 16 with PostGIS 3.4. Deployment is Docker Compose on one machine.
2. **Space.** The ward is the operational unit and the 250 m cell the modelling unit. Every stored geometry is typed with SRID 32644; EPSG:4326 appears only at API and sensor boundaries.
3. **Models.** M1 is a LightGBM susceptibility model with spatial cross-validation and a rank-scaled output. M2 is a LightGBM quantile forecaster of the change in drain level at +15, +30, +60 and +120 minutes with P10, P50 and P90, gated per horizon by skill. M3 is a calibrated logistic hazard function whose prior weights are labelled ASSUMED.
4. **Risk.** Hazard decides the permissible level band; impact selects inside the band; deterministic floors may raise a level using hazard evidence only; confidence governs process and never changes a level; data loss never lowers a level by itself; exposure and vulnerability can never override hazard gating.
5. **Numbers.** Every number shown to a person is produced by data, models, policy or geospatial computation. No language model produces, alters or approves a number, a level, a route or an instruction.
6. **Abstention.** Missing or stale evidence yields INSUFFICIENT\_EVIDENCE with a stated reason. The system never guesses and never shows a ward as safe.
7. **Labels.** Simulated data, prototype thresholds, uncalibrated hazard, synthetic validation and unverified sources are labelled wherever they appear, in the database, the API, the interface and every message. Simulated data is never presented as observed.
8. **Explanation.** Attribution uses the method stated in §20.2 with its label; exact Shapley values are called exact only when computed by full enumeration; approximations are labelled; every claim cites stored evidence.
9. **Agents.** There are six agents with typed contracts and tool wrappers. Agents cannot dispatch, approve or change reviews. The system runs and passes its tests with the language model disabled.
10. **Human approval.** An alert reaches DISPATCHED only if the database holds an approving review for the same alert version, created by a permitted role after a complete checklist. Reviews and audit rows are append-only and the audit log is hash-chained. Time is never consent.
11. **Delivery.** Public instruction text comes only from reviewed templates. Email goes to a sandbox inbox; SMS, IVRS and push are simulated and labelled. No citizen personal data is stored.
12. **Evaluation.** Every metric comes from the harness with a run id, includes baselines, uses events as the unit of independence, and carries its label. Targets in this guidebook are proposals, not results. Fewer than five independent events supports no claim.
13. **Learning.** Learning is offline, produces candidates only, and promotion needs a recorded human decision. There is no online learning and no automatic promotion.
14. **Security.** Device keys, passwords and tokens follow §30 and §36; secrets never enter the repository; the admin role cannot approve WARNING or URGENT alerts.
15. **Configuration.** Thresholds, weights and ramps live in versioned config files; changes during an active event need a restart and are audited.
16. **Reproducibility.** Seeds, config hash, data manifest hash and model hashes are stored with every run; the golden values in §38.5 and §43.4 are reproduced by the reference implementation.
17. **Demonstration.** The demo runs the scenario of §43 through the production code paths, uses the rule-selected demo area, and ships a recorded backup. Presenters state what is simulated.
18. **Definition of done.** The prototype is done when every item in §50 is ticked with evidence, tests T01 to T22 pass, CI is green, and three consecutive clean demo runs succeed on a clean machine.
